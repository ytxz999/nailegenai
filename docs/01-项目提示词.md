# 项目报告撰写提示词集（奶了个奶 · 三消堆叠消除小游戏）

> 项目暂定名：**奶了个奶**，机制与《羊了个羊》同类：多层堆叠牌面 + 7 格槽位 + 三张同图标消除。
> 本文件是**唯一操作手册**：我（AI）按 P00 → P10 逐条执行，每完成一条等你确认再进下一条。
> 本文件中一律**只写需求名称，不写 FR/AC 编号**——编号以 `docs/02-需求分析.md` 的实际产出为准，避免文档间编号漂移。

### 0.2 使用顺序

1. 先 P00 确认理解 → 2. P01 需求 → 3. P02 系统分析 → 4. P03 系统设计 → 5. P04 开发计划 → 6. P05 迭代 1～6 逐轮交付（每轮结束我人工试玩）→ 7. P06 改缺陷 → 8. P07 走查 → 9. P08 出骨架 → 10. P09 一次生成全文 → 11. P10 自查。

**编号纪律**：需求/规则/用例/验收的编号只在 `02` 文档里定义一次；后续文档、代码注释、提示词一律**引用编号**，不重新定义、不跳号、不改号。若基线确实要改，只能由你在 P01 阶段提出，改完升版本号（v1.0 → v1.1）后冻结。

### 0.3 交互记录采集（报告素材，越早做越省事）

每完成一个阶段，我在 `docs/07-AI交互记录.md` 追加一条，格式固定：

| 字段 | 要求 |
|---|---|
| 序号 | R-01、R-02…连续 |
| 时间 | 精确到分钟 |
| 提示词 | **原文照录**（可折叠长表格，但不得改写措辞） |
| AI 输出摘要 | 3～6 行：做了什么、产出哪些文件、关键决策 |
| 人工反馈 | 我看了什么、点了什么、结论是"通过"还是"不合格 + 原因" |
| 后续动作 | 进入下一阶段 / 发出 P06 修复提示词（附问题描述） |

> 这份记录是报告第 3、4 章的**唯一信息来源**。报告里的每一张提示词截图、每一段"AI 生成结果"，都必须能在这份记录里找到对应行。

### 0.4 三条铁律

1. **一次只做一件事**：文档阶段禁止写程序代码；编码阶段禁止回头改需求/设计文档（除非 P06 明确要求并记录）。
2. **基线不可推翻**：需求文档一经确认即冻结；后续只允许"提待确认问题"，不允许悄悄改需求。发现需求本身有错，走 P06 并在报告里如实记录这次返工——返工是加分项，隐瞒是减分项。
3. **留痕**：每个阶段的提示词 + 输出摘要 + 人工结论必须落进 `07`。没有记录的阶段视为没发生。

## P00 项目启动与约束提示词

```
你是面向对象项目开发助手。我们要一起完成《面向对象设计与分析》课程大作业：
开发一个"三消堆叠消除"小游戏（机制同《羊了个羊》），纯前端实现。

【技术约束】
- 原生 HTML + CSS + JavaScript，不用框架、不用构建工具、不用第三方库；
- 双击 index.html 即可运行，接口全部本地，不发任何网络请求；
- 关卡进度、最佳记录、设置存 localStorage；
- 渲染用 DOM + CSS（每张牌是一个绝对定位元素），不用 Canvas。

【游戏机制（复述用，不是最终需求）】
牌面由多层堆叠的牌组成，每张牌有一个图标；只有"正上方没有未消除的牌压着它"的牌才能点击。
点击后该牌飞入底部 7 格槽位；槽位中同图标凑满 3 张立即消除；槽位满 7 张且无法消除 → 失败；
牌堆全部清空 → 通关。道具：撤销（回退一步，含道具使用）、移出（把槽位里的牌移回牌堆顶）、洗牌（重排剩余牌图标）。

【本轮只做三件事，不要写代码、不要做需求文档】
1. 用不超过 10 行复述你对这个项目的理解（玩法一句话、核心难点一句话、你打算怎么分阶段）；
2. 列出你认为的"核心对象"清单（只写名字 + 一句话职责，8～14 个）；
3. 提出 3～5 个你现在就必须问清楚的问题（例如：牌堆分层怎么排布？道具次数是否有限？是否需要音效？）。

【禁止】输出任何 HTML/CSS/JS 代码；输出需求表格；自行决定上面没说的玩法细节。
```

**P00 后该做的事**：逐条回答那 3～5 个问题（答不上来的说"你给建议，我确认"），然后进入 P01。

## P05 迭代开发提示词（报告 3.4 AI 开发过程主体）

### P05 通用迭代模板

```
进入迭代 N：<迭代名称>。

【本轮目标】<一句话>
【需求依据】docs/02-需求分析.md 中的 <需求名称清单>；业务规则 <BR 名称清单>
【设计依据】docs/04-系统设计.md 的 <相关类与流程>

【仅允许改动】<文件/模块清单>
【禁止改动】docs/ 下任何文档；其它迭代已交付的模块（除非本轮明确要求）

【本轮必须做到】
1. 严格按设计中的类与方法签名实现，不得临时发明新类；
2. 业务逻辑不得直接操作 DOM：状态变更后通过统一的刷新入口更新界面；
3. 关键判定（覆盖、三消、失败、不变量）写成可单独调用的纯方法，便于我用浏览器控制台直接验证；
4. 代码写中文注释，说明"为什么"而不是"做了什么"；
5. 完成后给我：改动的文件清单 + 每个文件做了什么 + 我该怎么手工验证（3～5 步）+ 已知未完成项。

【完成后不要继续下一轮】等我说"通过"再进入下一条。
```

**迭代 1 项目骨架 + 数据模型 + 静态牌堆**

```
目标：页面能打开，能看到一个分层错位堆叠的牌堆（用占位图标），但还不能点击。
需求：牌堆展示、关卡配置的读取（只读）。
交付：index.html、css/main.css、js/model/Tile.js、js/model/Board.js、js/data/levels.js、js/model/Game.js（空壳）、js/view/Renderer.js（只渲染）。
约束：
- Tile 只负责自身数据与状态，不负责渲染；
- Board 负责分层与位置，负责"牌在屏幕上的坐标"的计算，渲染层只取值；
- 关卡配置写成数据，不允许把层数/牌数写死在渲染代码里。
验收：打开页面看到 3 层以上的错位牌堆；牌与牌有重叠；控制台能打印牌堆总张数与每层张数。
禁止：点击交互、消除、道具、存档、计时。
```

**迭代 2 交互核心（点击判定 → 入槽 → 三消 → 失败）**

```
目标：能真正玩起来——点可点的牌、进槽、凑三消除、槽满判负。
需求：覆盖判定、点击入槽、三消消除、槽位容量与失败判定。
交付：js/model/Tray.js、js/engine/Game.js（补全点击流程）、js/view/Renderer.js（补动画）、js/view/Input.js。
约束：
- 覆盖判定必须放在 Board 上，返回布尔值，不得掺入任何 DOM 判断；
- Tray 只负责槽位与三消，不负责计分与界面；
- 失败判定必须由"槽位满 7 且本次入槽后不产生三消"推导，不能写成"点了 7 次就输"；
- 一次点击的状态变更是原子操作：要么全部生效（入槽 + 可能的消除 + 可能的失败），要么完全不变。
验收：能完整玩到失败；能验证"被压住的牌点不动"；槽位中同图标 3 张立即消失；控制台可手工调用判定函数验证边界。
禁止：道具、关卡切换、存档、计时。
```

**迭代 3 关卡与生成器（三个难度 + 通关 + 计时步数）**

```
目标：三个难度都能开、都能通关，牌数正确，牌堆清空即通关。
需求：关卡配置、牌生成、3 的倍数不变量、通关判定、计时与步数、暂停。
交付：js/model/IconSet.js、js/engine/LevelGenerator.js、js/data/levels.js（三关配置）、js/engine/Timer.js、js/view/HUD.js。
约束：

- 关卡配置只写"层数、每层布局、图标种类数、总牌数"，具体哪张牌是什么图标由生成器决定；
- 计时器暂停时停止累加，恢复时继续，不允许出现"暂停后时间跳一下"；
- 生成算法要保证不会出现死局（生成时按三张一组投放到同一可解序列，说明你的做法）。
验收：三个关卡都能进入并无报错；总牌数分别为 60/108/144 且均为 3 的倍数；清空后弹出通关；计时与步数正确；暂停后不能操作。
禁止：道具、存档、最佳记录。
```

**迭代 4 道具（撤销 / 移出 / 洗牌）**

```
目标：三种道具都能用，次数有限，用错能撤销，且不破坏"3 的倍数"不变量。
需求：撤销、移出、洗牌、次数管理、道具的可撤销性。
交付：js/engine/Command.js（含具体命令类）、js/engine/UndoManager.js、js/engine/PropManager.js、js/view/PropBar.js。
约束：
- 每一次会改变状态的玩家动作都要生成命令对象，入栈；撤销 = 栈顶命令 undo()；
- 道具使用本身也是一条命令（撤销道具 = 归还次数 + 恢复牌面）；
- 移出：把槽位中前 3 张牌按原图标放回牌堆最上层，位置规则见设计文档，放回后仍可点击；
- 洗牌：只重排牌堆中未消除牌的图标，位置与覆盖关系不变，洗牌后必须重新自检不变量；
- 撤销栈上限与道具次数上限都写在配置里，不允许散落在代码中。
验收：连续点 10 次后连撤 10 次能回到开局牌面；用掉一次移出后撤销，移出次数恢复且槽位恢复；洗牌 20 次后不变量仍成立（可用控制台校验）。
禁止：改需求/设计文档；把道具逻辑写进 Renderer。
```

## 附录 B：写提示词的四条经验（可直接写进报告 3.4 末尾）

1. **先约束再要结果**：把"不许写代码""只允许改这几个文件"写进提示词，比事后返工便宜。
2. **把验收条件变成可执行的动作**：不说"判定要正确"，而说"控制台能手工调用函数验证边界"——否则 AI 会用界面现象冒充逻辑正确。
3. **一次只推进一层**：文档阶段不写代码，编码阶段不改文档；每轮结束必须能打开页面看到新东西。
4. **要求给出根因而非补丁**：P06 里"先定位根因再改"这一句，能把"改好了但不知道为什么"变成"改好了且知道为什么"。

## 附录 C：常见坑

| 坑 | 表现 | 预防 |
|---|---|---|
| 覆盖判定用 DOM 判断 | 缩放/滚动后判定错乱 | 判定只依赖模型数据（层号 + 坐标），与 DOM 无关 |
| 用"点了几次"判失败 | 槽位有 5 张但能三消时被误判 | 失败必须由"槽位满 7 且本次无消除"推导 |
| 撤销只回退牌不回退道具 | 撤销后道具次数变多 | 道具使用也封装成命令 |
| 洗牌破坏 3 的倍数 | 洗牌后出现"永远消不完" | 洗牌后自检不变量，失败则重洗 |
| 生成器产生死局 | 牌点完了槽位还剩同图标却放不进去 | 生成时按三张一组投放到同一可解序列 |
| 连点重复入槽 | 一次点击入两张 | 动画期间禁点 + 状态变更原子化 |
| 存档存了类实例 | 读档后方法丢失 | 只存普通对象，读档时重建实例 |
| 编号漂移 | 报告写 FR-05，02 文档里是 FR-07 | 编号只在 02 定义，别处只引用 |
