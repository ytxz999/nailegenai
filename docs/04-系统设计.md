## 1. 设计目标与边界

### 1.1 本阶段要回答的问题

分析阶段回答"谁负责什么"，本阶段回答"**怎么落地到代码**"：类的字段与方法、层间依赖、数据格式、界面尺寸、异常处理。三条硬约束贯穿全文：

| 约束 | 来源 | 在设计上的体现 |
|---|---|---|
| 判定不得依赖 DOM | BR-01、FR-07 | 牌的"可点性"只由 `layer / col / row` 三个整数决定，渲染坐标不进入判定（§3.3） |
| 数量不变量必须四条路径都守住 | BR-04、BR-05 | 生成、移出、洗牌、撤销四条路径各有一道自检，且共用同一个函数（§3.10、§6.4、§6.5） |
| 撤销不能靠"存快照回滚" | 分析决策 D-03 | 5 类命令各存**最小差量**（delta），不存整盘快照（§3.8） |

### 1.2 不在本阶段范围

- 不写任何可执行代码（本阶段只给签名与伪流程）。方法体、事件绑定细节、CSS 具体数值全部推迟到 P05。
- 不做性能优化（144 张牌在现代浏览器上无需优化；只在 §8 记一条"若卡顿"的退路）。
- 不做美术设计：牌面用 emoji / 纯色底 + 文字，避免引入图片资源与加载态。

### 1.3 技术选型一句话

原生 HTML + CSS + ES Module JavaScript，**无框架、无构建工具、无第三方运行时依赖**；视图用 **DOM 绝对定位**，不用 Canvas。理由见 §9 决策 DD-01。

## 2. 总体架构

### 2.1 四层划分

```
┌───────────────────────────────────────────────────────────────┐
│  表现层 View                                                  │
│  Renderer  BoardView  TrayView  HudView  DialogView           │
│  Animator  SoundPlayer   event-binder（点击 → Game 的转发）    │
└───────────────────────────┬───────────────────────────────────┘
                            │ 只读快照 + 订阅事件（单向）
┌───────────────────────────▼───────────────────────────────────┐
│  引擎层 Engine                                                │
│  Game   GameState   UndoManager   PropManager   Timer         │
│  LevelGenerator   TileFactory   EventBus                      │
└───────────────────────────┬───────────────────────────────────┘
                            │ 构造 / 调用 / 查询
┌───────────────────────────▼───────────────────────────────────┐
│  模型层 Model                                                 │
│  Tile   Board   Tray   LevelConfig   Command(+5 子类)         │
└───────────────────────────┬───────────────────────────────────┘
                            │ 只接受/产出纯数据
┌───────────────────────────▼───────────────────────────────────┐
│  数据层 Data                                                  │
│  Repository   StorageAdapter(schema / 校验 / 版本)            │
└───────────────────────────────────────────────────────────────┘
```

**与提示词给定的分层一一对应**：模型层 = Tile/Board/Tray/Level/Command；引擎层 = Game/UndoManager/PropManager/Timer/LevelGenerator；数据层 = Repository + localStorage；表现层 = Renderer + 事件绑定。多出的三个（EventBus / TileFactory / StorageAdapter）是层间粘合，放在各自所属层内，不新开层。

### 2.2 依赖方向与禁令

依赖只允许**从上往下**（表现 → 引擎 → 模型；引擎 → 数据）。逐条禁令是有原因的，不是教条：

| 编号 | 禁令 | 若违反会发生什么 | 检测手段 |
|---|---|---|---|
| DEP-1 | 模型层不得 import 引擎 / 数据 / 表现层任何模块 | Board 会开始知道"撤销栈"或"DOM"，单测必须造浏览器环境 | 全局搜索 `from '../engine` 在 `src/model/` 下应为 0 命中 |
| DEP-2 | 引擎层不得 import 表现层 | Game 会直接调 `renderer.refresh()`，于是"消除后刷新"与"消除逻辑"绑死，改界面就要改规则 | 搜索 `renderer` / `document` 在 `src/engine/` 下应为 0 命中 |
| DEP-3 | 表现层不得**写**模型：不能直接调 `tile.icon = ...` 或 `board.tiles.push(...)` | 任何界面 bug 都可能改坏局面；撤销栈与真实状态脱节 | 视图层只允许调 `game.xxx()` 与读取 `game.snapshot()` |
| DEP-4 | 数据层不得反向 import 引擎层 | Repository 会依赖 Game，存档结构跟着游戏流程变，无法独立演进 | 搜索 `from '../engine` 在 `src/data/` 下应为 0 命中 |
| DEP-5 | 命令对象不得持有 Game 引用 | 撤销时无法复用（Game 重建后旧命令失效），且形成环 | Command 只持 tileId 与位置等**值**，不持对象引用（§3.8） |

> DEP-5 是"命令模式"最常见的踩坑点：很多人把 `game` 塞进命令里，于是"撤销一条 30 步前的命令"实际是在操作一个已死对象。本项目命令只存**值**（id、层、格、图标、槽序号），执行时由 UndoManager 把当前 Game 的 `ctx` 传进去。

### 2.4 装配顺序（谁先 new 谁）

```
schema(常量) → StorageAdapter → Repository
             → TileFactory(IconSet) → LevelGenerator(LayoutStrategy)
             → Board / Tray / Timer / UndoManager / PropManager / GameState
             → Game
             → EventBus 订阅 → Renderer(各子视图) → main 绑定点击
```

只有 `main.js` 知道全部类型；其余模块只知道自己下游。这样"换视图"或"加求解器"都不用改引擎。

## 3. 类设计

> 约定：所有签名用 JS 形式书写；`#` 开头为私有字段；返回值类型用注释标注；**本阶段不含方法体**。

### 3.1 Tile（模型）—— 三态与位置自持

**状态机**（分析决策 D-02 的落地）：分析阶段给的是 `state ∈ {board, tray, cleared}`，设计阶段把迁移条件写死在这里，并规定**只允许 Board / Tray 改 state**。

```
        ┌──────────┐  Tray.append(t)   ┌──────────┐
        │  board   │ ───────────────▶  │   tray   │
        └────┬─────┘                   └────┬─────┘
             │                              │
             │ ▲      撤销（还原）           │ 三消命中
             │ └────────────────────────────┤
             │                              ▼
             │                        ┌──────────┐
             └───── 移出（回到 board）─│ cleared  │
                                      └──────────┘
```

| 字段 | 类型 | 说明 | 为什么需要 |
|---|---|---|---|
| `id` | string | 形如 `t07`，全生命周期唯一 | 命令只存 id，不存对象引用（DEP-5） |
| `icon` | string | 图标键，如 `'cat'` | 洗牌只改这个字段 |
| `layer` | int | 层号，0 起 | 覆盖判定第一维 |
| `col` / `row` | int | **半格单元**坐标（1 单元 = 牌宽/2） | 覆盖判定第二维；整数比较，无浮点 |
| `state` | enum | `board` / `tray` / `cleared` | 决定存在于哪个容器 |
| `group` | int | 生成时的"三张一组"编号 | 洗牌按组置换（§6.5）与可解性元数据 |
| `jitterX` / `jitterY` | int | −9～+9 px | 纯视觉（FR-06），**不参与任何判定** |

| 方法 | 签名 | 说明 |
|---|---|---|
| `constructor` | `(id, icon, layer, col, row, group)` | |
| `moveTo` | `(layer, col, row) → void` | **仅供 Board 调用**；不在 Board 内的牌调用即抛错 |
| `setState` | `(state) → void` | **仅供 Board / Tray 调用** |
| `faceRect` | `() → {x, y, size}` | 渲染用像素矩形（含 jitter），表现层用 |

> 设计要点：`moveTo` / `setState` 是"被容器调用的内部操作"，不是"牌自己能做的动作"。这条约束与不变式 I-1 配套：牌改了位置却没人改占用索引，是这类游戏最隐蔽的 bug。

### 3.2 LevelConfig（模型，不可变值对象）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | `beginner` / `advanced` / `challenge` |
| `name` | string | 显示名 |
| `layers` | int | 层数 |
| `cols` / `rows` | int | 每层格位行列数 |
| `tileCount` | int | 总牌数（= layers × cols × rows，生成器校验） |
| `iconKinds` | int | 图标种类数 |
| `perIconCount` | int | 每种图标张数 |
| `props` | `{undo, remove, shuffle}` | 道具次数 |
| `stageWidth` / `stageHeight` | int | 半格单元下的舞台尺寸，由布局策略算出 |

| 方法 | 签名 | 说明 |
|---|---|---|
| `validate` | `() → string[]` | 返回错误列表（空数组=通过）：`tileCount % 3`、`perIconCount % 3`、`perIconCount × iconKinds === tileCount`、`layers × cols × rows === tileCount`、道具次数 ≥ 0 |
| `groupCount` | `() → int` | `tileCount / 3` |
| `stageSize` | `() → {w, h}` | 由 `layers/cols/rows` 与错位规则算出的舞台半格尺寸 |

> `validate()` 在 `main.js` 装配时就跑一次；三个关卡配置是常量，若写错（例如改难度时把 108 写成 104）会在启动即报错，而不是等到某一关点不动。

### 3.3 Board（模型）—— 分层结构、覆盖关系、缓存

**数据结构**（三层各司其职，不要合并）：

| 字段 | 类型 | 作用 |
|---|---|---|
| `#tiles` | `Map<string, Tile>` | 牌堆内（state=board）的牌，主存储 |
| `#occupied` | `Map<string, Tile>` | 派生索引：键 `"layer:cell"` → 牌。**只为加速，可随时重建** |
| `#coverCount` | `Map<string, int>` | 派生索引：`tileId` → "覆盖它的牌数"，用于 O(1) 判断可点 |
| `#maxLayer` | int | 当前最高层号（移出溢出层时用） |
| `#cellSize` | int | 半格单元数（=2，即一张牌占 2×2 单元） |

**覆盖关系怎么算（核心算法，必须在设计阶段定死）**

两张牌重叠的判定（都换算成半格单元整数）：

```
overlaps(a, b) = |a.col - b.col| < 2 && |a.row - b.row| < 2
```

- 一张牌占 2×2 个半格单元，所以"同列同格"必然重叠（差 0）；"错开半格"（差 1）仍重叠 1 列；“错开一整张”（差 2）不重叠。
- 层间错位正是靠 `差 1` 制造出"半张牌压着两张牌"的经典堆叠手感。

可点判定：

```
canPick(t) = t.state === 'board' && coverCount[t.id] === 0
```

**缓存怎么维护**：`coverCount` 只在牌的**增删**时增量更新，不在每次点击时全量重算。

| 操作 | 对 `#occupied` / `#coverCount` 的影响 |
|---|---|
| `add(tile)` | 写入 `occupied`；遍历 `#tiles` 中 `layer > tile.layer` 且 overlaps 的牌，令 `coverCount[i]++` |
| `remove(tile)` | 删 `occupied`；遍历 `#tiles` 中 `layer > tile.layer` 且 overlaps 的牌，令 `coverCount[i]--` |
| 局面变化后自检 | `rebuildIndexes()`：丢弃两个派生索引，按 `#tiles` 全量重建 —— 只在**存档恢复**与**断言失败**时调用 |

- 复杂度：一次 `add/remove` 是 O(n)（n ≤ 144），一次点击最多一次 remove +（撤销时）一次 add，即每次操作 ≤ 2×144 次矩形比较。**不需要空间索引**（四分树/BVH 是过度设计，144 张牌下反而增加 bug 面）。
- 断言（开发模式下开启）：`rebuildIndexes()` 的结果与增量维护的结果逐项相等，否则抛出 —— 这条断言直接对着"缓存漂移"这个最难的 bug。

| 方法 | 签名 | 说明 |
|---|---|---|
| `constructor` | `(cellSize = 2) → Board` | |
| `add` | `(tile) → void` | 唯一入口：写索引 + 更新覆盖计数 |
| `remove` | `(tile) → void` | 唯一出口：删索引 + 更新覆盖计数 |
| `canPick` | `(tileId) → boolean` | O(1)，读 coverCount |
| `coverCountOf` | `(tileId) → int` | 调试与"压暗程度"分级用 |
| `get` | `(tileId) → Tile \| undefined` | |
| `all` | `() → Tile[]` | 渲染用（返回副本数组，防止外部改集合） |
| `size` | `() → int` | 剩余牌数 |
| `maxLayer` | `() → int` | |
| `findFreeCells` | `(layer) → {col, row}[]` | 某层的空格位（供移出落点，§6.4） |
| `addOverflowLayer` | `() → int` | 新建溢出层并返回层号（BR-07） |
| `groupTiles` | `() → Map<int, Tile[]>` | 按 group 分组（洗牌用） |
| `snapshot` / `restore` | `() → object` / `(data) → void` | 纯数据，供 Repository |
| `rebuildIndexes` | `() → void` | 恢复后与断言用 |

### 3.4 Tray（模型）—— 7 格与三消

| 字段 | 类型 | 说明 |
|---|---|---|
| `#slots` | `(Tile \| null)[]` | 固定长度 7；`null` 表示空格。**有洞**（撤销后中间会空一格），不能假设紧凑 |
| `#capacity` | int | 7（常量，但做成字段便于测试边界） |

| 方法 | 签名 | 说明 |
|---|---|---|
| `append` | `(tile) → int` | 追加到第一个 `null` 位置，返回槽序号；满则返回 −1 |
| `removeAt` | `(index) → Tile \| undefined` | 撤销用 |
| `takeFirst` | `(count) → Tile[]` | 移出道具取最早 count 张（按槽序，跳过 null） |
| `findTriple` | `(icon) → int[]` | 返回该图标在槽内的 3 个槽序号，不足 3 返回 `[]` |
| `indexOf` | `(tileId) → int` | |
| `size` | `() → int` | 非 null 的数量 |
| `isFull` | `() → boolean` | `size === capacity` |
| `isEmpty` | `() → boolean` | |
| `toArray` | `() → (Tile \| null)[]` | 渲染用副本 |
| `snapshot` / `restore` | 同上 | 纯数据 |

**三消检测（BR-03）**：入槽后只检测**刚放入的那张牌的图标**是否在槽内达到 3 张 —— 不扫描全槽。理由：一次入槽最多让一个图标达到 3 张（其余图标数量未变），全槽扫描是多余工作，且会让"一次触发两组消除"成为可能，与 BR-03"一次入槽最多触发一次消除"冲突。

**关于"三消连锁"**：本项目**不存在连锁**。连锁的前提是"消除后触发新的配对"，而本项目的配对只由入槽产生；消除不产生新牌。这条在 §6.1 里明确写出，避免实现时被"三消游戏"的既有印象带偏。

### 3.5 IconSet（模型，只读）

| 字段 | 类型 | 说明 |
|---|---|---|
| `#all` | `{key, label, bg, fg}[]` | 全量图标定义，固定 10 个（emoji + 配色），按 `iconKinds` 取前 N 个 |
| `#pool` | `string[]` | 本局实际可用的图标键 |

| 方法 | 签名 | 说明 |
|---|---|---|
| `pick` | `(kinds) → string[]` | 取前 k 个图标键；`kinds > 10` 时抛错（配置错误要早死） |
| `styleOf` | `(key) → {bg, fg, label}` | 渲染用 |

固定 10 个图标而不是随机生成颜色：一是 emoji 可直接用系统字体，零资源；二是**图标的"可区分度"是难度的一部分**，随机配色会做出"两种颜色肉眼难分"的坏局面（真实三消游戏都靠美术保证可区分度，这里用硬编码列表替代美术）。

### 3.6 TileFactory（引擎）

| 方法 | 签名 | 说明 |
|---|---|---|
| `constructor` | `(iconSet) → TileFactory` | |
| `create` | `(icon, layer, col, row, group, seq) → Tile` | `seq` 用于生成 `id = 't' + String(seq).padStart(3,'0')` |
| `resetCounter` | `() → void` | 重开时归零，保证 id 不与旧局冲突（旧局对象已整体废弃） |

**为什么需要它**：id 必须是全生命周期唯一的，而"唯一"只有集中发号才能保证。若各处 `Math.random()` 造 id，撤销时按 id 找牌会撞车。工厂同时负责 `jitter` 的随机生成（`±9px`），把"视觉随机"钉在一个地方，方便 P05 关掉随机做截图对比。

### 3.7 LevelGenerator（引擎）—— 生成即保证 3 的倍数 + 难度可控

这是全项目算法最重的一处，设计成**三步流水线**，每步都有明确输出与自检：

```
① 布局（LayoutStrategy）        ② 拓扑序（决定点击顺序）        ③ 贴图标（按组）
   layers × cols × rows           从"最终状态"反向剥离             每 3 个连续位置一组
   → 全部格位坐标                  → 一个合法的可清空序列 S        → 同组同图标
```

**① 布局**：由 `LayoutStrategy` 产出 `{layer, col, row}` 列表。规则是层内网格 + 层间半格错位：

```
col = 2 * c + (layer % 2)          // c ∈ [0, cols)
row = 2 * r + (layer % 2)          // r ∈ [0, rows)
```

舞台半格尺寸：`stageW = 2*(cols-1) + 2 + 1`（末项 1 为错位余量），`stageH = 2*(rows-1) + 2 + 1`。

**② 拓扑序**：反向剥离法。维护"已剥离集合"，反复从剩余牌中挑出**当前不被任何上层牌覆盖**的牌加入序列尾部，直到取完。等价于按"层号从高到低 + 同层内随机打乱"的 Kahn 拓扑排序：

```
S = []
remaining = 全部格位
while remaining 非空:
    pickable = { p ∈ remaining | 不存在 q ∈ remaining, q.layer > p.layer 且 overlaps(p,q) }
    // 注意：用 remaining 而非全量做覆盖判断，因为"先被剥离的牌已经消失"
    if pickable 为空: 抛出"布局不可解"（理论上不会，层内不重叠保证了每层至少有一批可剥离）
    从 pickable 中随机取一个 p（同层内随机 = 打散图标分布）
    S.push(p); remaining.remove(p)
```

- **为什么用反向剥离而不是"从上往下逐层铺"**：直接按层号倒序取，同层内会形成"从左到右"的规律图标走向，玩家一眼看穿。反向剥离在每一轮都重新计算可剥离集合，同层随机取，得到的序列在空间上更分散。
- **注意覆盖判定的基准**：判断"p 是否可剥离"时，要看的是**仍在 remaining 里的牌**，不是全量牌堆。这是反向剥离与"正向判定"最容易写错的一处 —— 正向判定问"现在能不能点"，反向剥离问"它消失时是不是已经没东西压着它"。

**③ 贴图标**：`S` 每 3 个连续位置为一组，同组贴同一个图标；图标按 `iconKinds` 轮转分配（每种恰好 `perIconCount/3` 组）。

```
groups = chunk(S, 3)                      // 组数 = tileCount/3
for i in 0..groups.length-1:
    icon = pool[ i % iconKinds ]
    for pos in groups[i]: 创建 Tile(icon, pos.layer, pos.col, pos.row, group=i)
```

- **为什么这样就能保证"3 的倍数"**：每种图标的牌数 = `该图标组数 × 3`，构造上就是 3 的倍数；总数 = `组数 × 3`。不需要生成后再"调数量"，因此不会出现"某种图标 3k+1 张"的死局。
- **为什么这样就能保证"可解"（BR-12）**：按 `S` 的顺序点击，前 3 张同图标立刻消除，槽位最多同时存 3 张 → 永不超过 7，且每 3 步清空一次。**存在性证明是构造性的，不是概率性的**。
- **难度如何可控**（提示词第 2 点要求）：难度由四个可调参数决定，全部写在 `LevelConfig` 里：

| 参数 | 影响 | 入门 | 进阶 | 挑战 |
|---|---|---|---|---|
| `layers` | 层数越多，可点牌越少，"选择"越受限 | 4 | 6 | 9 |
| `iconKinds` | 种类越多，槽里凑齐 3 张的概率越低（干扰越大） | 5 | 6 | 8 |
| 每层格位密度 | `cols×rows` 越大，同层可选越多，反而更简单 | 5×3=15 | 6×3=18 | 4×4=16 |
| 错位策略 | 固定半格错位；若改为随机错位，覆盖关系更复杂 | 固定 | 固定 | 固定 |

- **可解序列 S 是否要保存**：要。S 的"组号"信息写进 `Tile.group`，洗牌按组置换（§6.5）依赖它；S 本身（位置顺序）**不保存**，因为它可由 `group` 与层号重建，且存了反而可能与实际局面不一致。

| 方法 | 签名 | 说明 |
|---|---|---|
| `constructor` | `(tileFactory, layoutStrategy) → LevelGenerator` | |
| `generate` | `(config) → {tiles: Tile[], board: Board, solutionGroups: Map<int, Tile[]>}` | 三步流水线 |
| `#buildLayout` | `(config) → Pos[]` | ① |
| `#topoOrder` | `(positions) → Pos[]` | ② |
| `#assignIcons` | `(order, config, pool) → Tile[]` | ③ |
| `#assertInvariants` | `(tiles) → void` | 数量不变量自检（失败则抛错，由 Game 捕获后重试一次） |

> 自检失败的处理：`generate` 外层包一次重试；两次都失败则降级为"顺序铺"（把 S 直接取为按层倒序），并在控制台记录 `GENERATOR_FALLBACK`。这条降级路径只在配置被改坏时触发，正常情况下永不进入 —— 但它保证了"配置写错也不会让游戏白屏"。

### 3.8 Command 体系（模型）—— 一条 undo() 收口 5 类操作

**统一契约**：

```js
class Command {
  get type()                       // 'enter' | 'remove' | 'shuffle' | ...
  undo(ctx)                        // ctx = { board, tray, propManager, game }
  describe()                       // 中文短描述，用于调试面板/日志
}
```

**5 个具体命令与各自的最小差量**：

| 命令 | 触发 | 存什么（delta） | undo 做什么 |
|---|---|---|---|
| `EnterTrayCommand` | 点击可点牌（FR-08） | `tileId, from:{layer,col,row}, slotIndex, cleared?: [{tileId, icon, slotIndex, group}]` | ① 把牌从槽位移回牌堆原位；② 若有 `cleared`，把 3 张按原 slotIndex 放回槽位并置 `state=tray` |
| `RemoveCommand` | 移出道具（FR-18） | `moved:[{tileId, fromSlot, to:{layer,col,row}}], createdLayer?: int` | 把 3 张牌从牌堆移回原槽位；若 `createdLayer` 存在且该层已空，删掉该层并回退 `maxLayer` |
| `ShuffleCommand` | 洗牌道具（FR-19） | `before: Map<tileId, icon>`（只存被换动的牌） | 逐张恢复图标 |
| `PropConsumeCommand` | **不单独成命令** | — | 道具次数随对应命令一起回退（见下） |
| `RestartCommand` | 重开（FR-05） | **不用于撤销**：重开会清空撤销栈 | — |

**关键设计点 1：道具次数不单独成命令**

"用掉一次撤销""用掉一次洗牌"不是一个独立操作，而是**附着在效果命令上的属性**。若单独记一条命令，就会产生"撤销了洗牌但次数没还"的错位。所以：

| 道具 | 命令 | 次数回退时机 |
|---|---|---|
| 撤销 | `UndoManager` 自身不产生命令；**撤销本身不可撤销**（BR-06） | 撤销操作把"被撤销命令消耗的道具次数"还给 PropManager |
| 移出 | `RemoveCommand` | `undo()` 内调 `propManager.refill('remove')` |
| 洗牌 | `ShuffleCommand` | `undo()` 内调 `propManager.refill('shuffle')` |

> 注意 BR-06 的措辞是"撤销后牌回到原位、道具次数归还"。这里的"归还"指的是**被撤销的那条命令**消耗的次数（例如撤销一次移出，移出的次数还回来），而不是"撤销这个动作本身免费"。撤销本身的次数在 `UndoManager` 里扣，且不可通过撤销找回 —— 否则玩家可以无限撤销（撤销一次洗牌，再用撤销取消"取消洗牌"，次数不变）。

**关键设计点 2：为什么存 delta 而非快照**

| 方案 | 单条命令内存 | 30 条栈 | 正确性风险 |
|---|---|---|---|
| 全量快照（144 张牌深拷贝） | ~144 × 6 字段 ≈ 5KB | ~150KB | 低，但"恢复后对象引用全变"，视图与命令持有的旧引用失效 |
| **最小 delta（本方案）** | 3～4 张牌的 id 与坐标 ≈ 200B | ~6KB | 需要严格定义"撤销的逆操作"，但有 §9 的断言兜底 |

选 delta 的决定性理由不是内存，而是**引用稳定性**：快照恢复会重建 Tile 对象，而 DOM 节点、进行中的动画、命令里的 tileId 都指向旧对象，需要全局重建 —— 一次撤销引发全量重渲染，体验与代码复杂度都差。

**关键设计点 3：命令只存值，不存对象（DEP-5）**

`undo(ctx)` 里通过 `ctx.board.get(tileId)` 取当前对象。这样"撤销栈跨重开仍可清空"、"命令可被序列化（未来做回放）"都成立。

### 3.9 UndoManager（引擎）

| 字段 | 类型 | 说明 |
|---|---|---|
| `#stack` | `Command[]` | 容量 30 |
| `#limit` | int | 30（BR-06） |
| `#suppressed` | boolean | 撤销/应用中，防止命令内操作再次入栈 |

| 方法 | 签名 | 说明 |
|---|---|---|
| `push` | `(cmd) → void` | 超限时 `shift()` 丢弃最旧，并记 `console.debug` |
| `canUndo` | `() → boolean` | `!suppressed && stack.length > 0 && 状态可撤销 && 道具次数 > 0` |
| `undo` | `(ctx) → {ok, cmd?}` | 弹出栈顶 → `cmd.undo(ctx)` → 返回被撤销命令 |
| `clear` | `() → void` | 重开 / 换关 / 读档时调用 |
| `size` | `() → int` | |

**为什么 `canUndo` 要检查状态**：终局（Won/Lost）后 BR-09 要求一切操作无效，包括撤销。这个判断放在 `canUndo` 里而不是按钮的地方，保证"按钮置灰"与"逻辑拒绝"用同一处真相。

### 3.10 PropManager（引擎）—— 只做次数与准入

| 字段 | 类型 | 说明 |
|---|---|---|
| `#counts` | `{undo, remove, shuffle}` | 剩余次数 |
| `#initial` | 同上 | 初值（重开时恢复） |

| 方法 | 签名 | 说明 |
|---|---|---|
| `init` | `(props) → void` | 按关卡配置写入初值 |
| `countOf` | `(kind) → int` | |
| `canUse` | `(kind, ctx) → {ok, reason?}` | 准入四查：次数 > 0、状态允许、局面有意义（如槽位非空才能移出）、撤销栈非空 |
| `consume` | `(kind) → void` | 扣 1 |
| `refill` | `(kind) → void` | 还 1（撤销回退用），不超过初始值 |
| `reset` | `() → void` | 重开恢复初值 |

**"局面有意义"的判定为什么要在这里**：`canUse` 是"按钮是否可点"与"逻辑是否允许"的**唯一来源**。若把"槽位空了不能移出"写在按钮里，键盘触发或程序调用就能绕过。

### 3.11 Timer（引擎）—— 累计毫秒，不每秒自增

| 字段 | 类型 | 说明 |
|---|---|---|
| `#accumulated` | int | 已累计毫秒（跨暂停保留） |
| `#startedAt` | int \| null | 本段开始时刻（`performance.now()`） |
| `#running` | boolean | |

| 方法 | 签名 | 说明 |
|---|---|---|
| `start` | `() → void` | 若已运行则忽略 |
| `pause` | `() → void` | `accumulated += now - startedAt`，置 `running=false` |
| `resume` | `() → void` | 重新记 `startedAt` |
| `stop` | `() → void` | 结算时调用，等价于 pause |
| `elapsedMs` | `() → int` | `accumulated + (running ? now - startedAt : 0)` |
| `format` | `() → string` | `mm:ss`（超过 99 分钟不特殊处理，课程作业不会出现） |
| `reset` | `() → void` | 重开归零 |

**为什么不每秒 `+1`**：`setInterval(1000)` 会漂移（浏览器节流、标签页后台），10 分钟能差出十几秒；而"暂停期间不累加"（BR-10）用自增模型根本无法准确实现。累计毫秒模型下，暂停只是"把当前段结算进 accumulated"。显示刷新用独立的 250ms 定时器读 `elapsedMs()`，与计时逻辑解耦。

**步数不在这里**（闭环 P-01）：FR-22 说"每次成功入槽计 1 步"，这是**对局统计**不是时间量；放 Timer 会让 Timer 有两个变化轴。步数归 `Game.stats.moves`。

### 3.12 Repository / StorageAdapter（数据层）

**分层理由**：Repository 管"业务语义"（保存什么、裁剪规则、损坏降级），StorageAdapter 管"介质"（localStorage 读写、JSON 编解码、容量异常）。这样"换存储介质"（比如改成 IndexedDB 或导出文件）只改 Adapter。

| 类 | 方法 | 签名 | 说明 |
|---|---|---|---|
| StorageAdapter | `read` | `(key) → any \| null` | 解析失败返回 null 并上报 |
| | `write` | `(key, value) → boolean` | 失败（QuotaExceeded / 隐私模式）返回 false |
| | `remove` | `(key) → void` | |
| | `isAvailable` | `() → boolean` | 启动时探测一次 |
| Repository | `saveGame` | `(game) → boolean` | 序列化进行中对局 |
| | `loadGame` | `() → Snapshot \| null` | 校验版本与结构，失败返回 null |
| | `clearGame` | `() → void` | 通关/失败/重开时清 |
| | `loadBest` | `() → BestRecords` | |
| | `submitBest` | `(levelId, {timeMs, moves}) → {isNew, rank}` | 更新并裁剪 |
| | `loadSettings` / `saveSettings` | `() → Settings` / `(s) → void` | |
| | `migrate` | `(raw) → any \| null` | 版本不匹配时的迁移/丢弃 |

**Repository 只搬纯数据**（分析决策 D-10）：它不 `new Tile()`，只把 `{id, icon, layer, col, row, state, group}` 平铺出来；恢复时由 Game 调 `TileFactory` 重建。这样存档格式与类结构解耦，加字段不会破旧档。

| 字段 | 类型 | 说明 |
|---|---|---|

### 3.15 GameState（引擎）—— 单枚举 + 迁移表

| 状态 | 含义 | 允许的操作 |
|---|---|---|
| `Idle` | 未进入任何关卡（选关界面） | 选关 |
| `Ready` | 已加载牌堆，未开始计时 | 开始 |
| `Playing` | 进行中 | 点击、道具、暂停、重开 |
| `Paused` | 暂停 | 继续、重开、返回 |
| `Won` | 通关 | 重开、返回、下一关（本期不做） |
| `Lost` | 失败 | 重开、返回 |

| 方法 | 签名 | 说明 |
|---|---|---|
| `constructor` | `() → GameState` | 初始 `Idle` |
| `current` | `() → string` | |
| `can` | `(action) → boolean` | 按迁移表判断，`action ∈ {select, start, click, prop, pause, resume, restart, back}` |
| `transition` | `(to) → boolean` | 非法迁移返回 false 并 `console.warn`，**不改状态**（宁可不动，也不要进入诡异中间态） |
| `isTerminal` | `() → boolean` | `Won || Lost` |

**为什么不用 6 个布尔标志**：`paused` / `won` / `lost` / `started` 四个布尔能组合出 16 种状态，其中 10 种是非法但可表达的（`paused && won`），每个用到状态的地方都要自己判断组合 —— 这是状态类 bug 的温床。单枚举把"合法集合"压缩到 6 个，迁移表是唯一真相。

### 3.16 Renderer 与子视图（表现层）

| 类 | 关键方法 | 说明 |
|---|---|---|
| `Renderer` | `mount(root)` / `renderAll(snapshot)` / `onEvent(evt, payload)` | 订阅 EventBus，分派给子视图；持有 `Animator` 与 `SoundPlayer` |
| `BoardView` | `render(tiles, canPickMap)` / `pick(tileId)` / `markPickable(map)` | 只创建/更新牌节点，**不重建整棵 DOM**（避免动画中断） |
| `TrayView` | `render(slots)` / `flashCleared(indices)` | 7 格固定节点，改内容不改结构 |
| `HudView` | `render({level, remaining, time, moves})` / `setLocked(bool)` | |
| `PropBar` | `render(counts, canUseMap)` | 按钮 `disabled` + `aria-disabled` 双写 |
| `DialogView` | `show(kind, payload)` / `hide()` | `kind ∈ {result, pause, help, confirm-restart}` |
| `Animator` | `flyToTray(tileId, from, to)` / `clearTiles(ids)` / `shake(tileId)` / `shuffleFaces(ids)` / `loseShake()` | 返回 Promise，`prefers-reduced-motion` 时立即 resolve |
| `SoundPlayer` | `play(name)` / `setEnabled(bool)` | WebAudio 合成，无音频文件 |

**视图的三条纪律**：

1. **视图不判定**：`BoardView` 不计算"能不能点"，只渲染 `canPickMap`（由 Game 传来的 `coverCount` 导出）。
2. **视图不改模型**：点击只调 `game.clickTile(id)`，不改任何 `tile` 字段（DEP-3）。
3. **视图可丢弃**：`renderAll(snapshot)` 必须能从任意快照完整重建界面 —— 这是"刷新恢复"（FR-25）能在视图层零成本实现的前提。

## 4. 设计模式

五个模式都对应本项目里**一个具体的、能指出行号的问题**；解决不了具体问题的模式一律不用（例如"装饰器"在这里只能装饰按钮样式，等于给自己加一层调用栈）。

### 4.1 观察者 —— 一次操作要刷新 5 个地方

| 项 | 内容 |
|---|---|
| 解决的具体问题 | 一次成功入槽要同时更新：牌堆（少一张 + 可点性变了）、槽位（多一张）、HUD（剩余牌数、步数）、道具条（撤销可用性）、弹窗（可能结算）。若 Game 逐个 `view.xxx()` 直调，Game 就依赖 DOM，且新增一个显示项要改 Game。 |
| 本项目的实现 | `EventBus`；Game 只 `emit`，Renderer 只 `on`。事件清单见 §3.13，**封闭集合**。 |
| 为什么不用更简单的"回调注入" | 回调注入在订阅者只有 1 个时更省事，但本项目有 6 个子视图，Game 要持 6 个回调；且"弹窗"是后创建的，回调要动态注册 —— 那就是个简化版 EventBus。 |
| 不用的后果 | Game 里出现 `document.querySelector`，模型层无法单测；"刷新漏了一处"成为常态 bug。 |

### 4.2 命令 —— 撤销 5 类异构操作

| 项 | 内容 |
|---|---|
| 解决的具体问题 | 要撤销的操作有 5 类：点击入槽（可能连带消除 3 张）、移出（可能新建溢出层）、洗牌（换了一批图标）。它们的逆操作**完全不同**，但"撤销"按钮只有一个。 |
| 本项目的实现 | `Command` 抽象 + 5 个子类，统一 `undo(ctx)`；`UndoManager` 只认接口（§3.8）。 |
| 为什么不用"每类操作一个 undo 函数 + switch" | 也能工作，但"新增一类操作"要改 3 处（入栈、switch、按钮可用性）；且命令对象天然携带 delta，switch 版本容易在函数里重新推导 delta 而出错。 |
| 不用的后果 | 撤销只能退化为"重开"，而 FR-17 明确要求撤销上一步。 |

### 4.3 工厂 —— id 唯一性与"造一局牌"

| 项 | 内容 |
|---|---|
| 解决的具体问题 | ① Tile 的 id 必须全局唯一（命令按 id 找牌）；② 一局牌要按三步流水线批量构造，涉及 Board 索引建立；③ 关卡生成算法要能整体替换（策略）而不改 Game。 |
| 本项目的实现 | `TileFactory`（单张，集中发号 + jitter）+ `LevelGenerator`（整体，三步流水线）。 |
| 为什么拆成两个工厂 | 职责完全不同：前者回答"怎么造一张合法的牌"，后者回答"造哪些牌"。合成一个会让"存档恢复也要造牌"（只需 TileFactory）被迫走一遍关卡生成流程。 |
| 不用的后果 | 存档恢复时若复用生成器，会重新跑拓扑序，得到的 group 与原局不同 → 洗牌按组置换的语义破裂。 |

### 4.4 状态 —— 六个局面的"谁能做什么"

| 项 | 内容 |
|---|---|
| 解决的具体问题 | 暂停时不能点牌、终局后只能重开、动画期间忽略点击、`Ready` 与 `Playing` 的区别是"开始计时"。若用布尔组合，每个入口都要自己判断。 |
| 本项目的实现 | `GameState` 单枚举 + 迁移表 + `can(action)`；所有入口先问 `can`（§3.15）。 |
| 为什么不把状态分散到各对象 | 例如"暂停"由 Timer 管、"终局"由 Game 管，就会出现"计时停了但还能点牌"的不一致。单一状态对象保证"停"是原子的。 |
| 不用的后果 | 典型 bug：暂停中点牌仍能入槽（Timer 停了但牌没锁）。 |

### 4.5 策略 —— 布局与洗牌是可替换算法

| 项 | 内容 |
|---|---|
| 解决的具体问题 | ① 布局算法（层内网格 + 层间错位）未来可能改成"随机散点"，且挑战关可能需要更密的排布；② 洗牌算法有"分组置换"与"完全随机"两种取舍（§9 DD-06），需要能切换对比验收。 |
| 本项目的实现 | `LayoutStrategy`（`buildPositions(config) → Pos[]`）、`ShuffleStrategy`（`plan(board) → Map<tileId, icon>`）。默认实现分别是 `GridParityLayout` 与 `GroupPermutationShuffle`。 |
| 为什么这两个"值得"策略化 | 它们是唯一两处"换算法不改流程"的地方：Game 与 Board 都只调接口。其他类（如 Tray）内部只有一种合理实现，策略化只增加阅读成本。 |
| 不用的后果 | 想对比"分组置换"与"完全随机"哪个体验好，要改 Board 内部代码，且改动会污染撤销语义。 |

## 5. 数据设计

### 5.1 localStorage 键与版本

| 键 | 内容 | 版本字段 | 写入时机 |
|---|---|---|---|
| `nailegenai.save` | 进行中的对局（**只有一份**，最近进入的关卡） | `v: 1` | 每次成功操作后（节流 300ms）、切后台、退出前 |
| `nailegenai.best` | 三关最佳记录 | `v: 1` | 通关时 |
| `nailegenai.settings` | 音效/动效开关、是否看过说明 | `v: 1` | 改动即写 |

统一前缀 `nailegenai.`，便于"重置全部数据"时按前缀清理，也不会与同域其他页面冲突。

### 5.2 存档结构

```js
{
  v: 1,
  savedAt: 1793512345678,          // 毫秒时间戳
  levelId: 'advanced',
  configHash: 'advanced:6:6:3:18',  // 关卡参数指纹，参数改了则本档作废
  status: 'Playing',               // 'Playing' | 'Paused'
  elapsedMs: 187300,
  moves: 42,
  props: { undo: 1, remove: 1, shuffle: 1 },
  propsInitial: { undo: 2, remove: 1, shuffle: 1 },
  tiles: [                          // 只存未消除的牌（state ≠ cleared）
    { id: 't001', icon: 'cat', layer: 0, col: 0, row: 0, state: 'board', group: 0 },
    { id: 't002', icon: 'cat', layer: 0, col: 2, row: 0, state: 'tray',  group: 0 }
  ],
  tray: ['t002', null, 't017', null, null, null, null],   // 长度恒为 7，null 占位
  maxLayer: 5,
  overflowLayers: []                // 移出新建的层号，撤销/恢复时用
}
```

**刻意不存的三样东西**：

| 不存 | 理由 | 代价 |
|---|---|---|
| 撤销栈 | 命令序列化 + 恢复后对象重建，复杂度高；且"刷新后还能撤销上一步"不是需求（FR-25 只要求"完整恢复对局"） | 刷新后撤销按钮置灰，界面给一行提示"刷新后不可撤销" |
| `jitter` | 纯视觉，重算即可（同一张牌抖动变了看不出来） | 无 |
| 可解序列 S | 由 `group` + 层号可重建；存了反而可能不一致 | 无 |

### 5.3 三关配置与验算

| 参数 | 入门 beginner | 进阶 advanced | 挑战 challenge |
|---|---|---|---|
| 层数 `layers` | 4 | 6 | 9 |
| 每层格位 `cols × rows` | 5 × 3 | 6 × 3 | 4 × 4 |
| 每层牌数 | 15 | 18 | 16 |
| 总牌数 `tileCount` | **60** | **108** | **144** |
| 图标种类 `iconKinds` | 5 | 6 | 8 |
| 每种张数 `perIconCount` | **12** | **18** | **18** |
| 组数 `groupCount` | 20 | 36 | 48 |
| 道具（撤销/移出/洗牌） | 3 / 2 / 2 | 2 / 1 / 1 | 1 / 1 / 1 |

**逐条验算**（对应 `LevelConfig.validate()` 的五条规则）：

| 关卡 | ① 层×格=总数 | ② 总数 % 3 | ③ 每种 % 3 | ④ 每种×种类=总数 | ⑤ 组数=总数/3 |
|---|---|---|---|---|---|
| 入门 | 4×15 = 60 = 60 ✓ | 60 % 3 = 0 ✓ | 12 % 3 = 0 ✓ | 12 × 5 = 60 ✓ | 60/3 = 20 ✓ |
| 进阶 | 6×18 = 108 = 108 ✓ | 108 % 3 = 0 ✓ | 18 % 3 = 0 ✓ | 18 × 6 = 108 ✓ | 108/3 = 36 ✓ |
| 挑战 | 9×16 = 144 = 144 ✓ | 144 % 3 = 0 ✓ | 18 % 3 = 0 ✓ | 18 × 8 = 144 ✓ | 144/3 = 48 ✓ |

**难度三参数的实际效果**（为什么挑战是 9 层 / 8 种 / 4×4）：

| 参数变化 | 对玩家决策的影响 | 挑战关取值 |
|---|---|---|
| 层数 ↑ | 同层可点牌被上层挡住的比例 ↑，"能选的牌"变少，误点概率 ↑ | 9（入门 4） |
| 图标种类 ↑ | 槽里 7 格能容纳的"半成品"种类有限，种类越多越容易堆满 | 8（入门 5） |
| 每层格位 ↓ | 同层可选少，且 4×4 使上下层重叠率更高 | 16（进阶 18） |

> 挑战关的可解性**不降低**（BR-12 构造性保证），降低的是"找得到那条序列"的概率。这是 P00 里把"恶意难度"翻译成可验收参数的结果，也是 AC-33 能写出明确判定标准的前提。

### 5.4 最佳记录结构与裁剪

```js
{
  v: 1,
  records: {
    beginner:  [ { timeMs: 154000, moves: 58, at: 1793512000000, props: 2 }, ... ],
    advanced:  [],
    challenge: []
  }
}
```

| 规则 | 值 | 说明 |
|---|---|---|
| 每关保留条数 | **5 条** | 课程作业体量下 5 条足够看清"自己在进步"，多了反而看不出 |
| 排序 | 用时升序，用时相同按步数升序 | |
| 入榜条件 | 比第 5 名更优，或不足 5 条 | |
| 并列处理 | 完全相同时保留更早的一条（"先到"） | 避免刷同一成绩反复覆盖 |
| 展示 | 选关界面显示第 1 条为"最佳"，结算界面显示"新纪录"标记（当且仅当提交后 rank === 0） | |

**为什么不全量保留**：localStorage 单域约 5MB，全量保留虽不至于爆，但"记录越攒越多、排序越慢"是无收益的复杂度；且学生演示时看到 5 条恰好能体会"排名"机制。

### 5.5 默认设置

```js
{ v: 1, sound: true, reduceMotion: false, helpSeen: false }
```

- `sound` 默认开（FR-26 要求），但**首次交互前不播放任何声音**（浏览器自动播放策略：AudioContext 需用户手势后才能 resume）。这条在 P05 实现时容易漏，导致"设置里音效是开的，但没有声音"。
- `reduceMotion` 默认关；开启后 `Animator` 的所有动画立即 resolve（`prefers-reduced-motion` 媒体查询也走同一开关，二者取"或"）。
- `helpSeen` 用于首次进入时自动弹玩法说明（只弹一次）。

## 6. 关键流程设计

> 每个流程都写成"先做什么、后做什么"，并标出**失败分支**与**不变量检查点**。

### 6.1 点击一张牌并触发消除（对应时序图 `04-时序图-点击消除.puml`）

| 步 | 动作 | 失败/分支 |
|---|---|---|
| 1 | BoardView 收到 click → 取 `data-tile-id` → 调 `game.clickTile(id)` | id 不存在 → 返回 `{ok:false, kind:'noop'}`，不报错（DOM 可能已过期） |
| 2 | Game 查 `state.can('click')` | `Paused/Won/Lost` → 拒绝；`#locked`（动画中）→ 拒绝但**不提示**（避免动画期间误触弹出噪音） |
| 3 | Game 查 `board.get(id)` | 不在牌堆（已在槽位/已消除）→ 拒绝 |
| 4 | Game 调 `board.canPick(id)` → 即 `coverCount === 0` | **被覆盖** → `emit('tile:rejected', {reason:'covered'})`，播放抖动 + 提示音（FR-11）；**不增步数、不入栈、不改状态** |
| 5 | Game 构造 `EnterTrayCommand`，先取 `from = {layer, col, row}` | — |
| 6 | `board.remove(tile)` → 更新 `occupied` 与 `coverCount` | — |
| 7 | `tray.append(tile)` → 返回 `slotIndex`；`tile.setState('tray')` | 满则返回 −1：**不应发生**（满 7 时上一步就该失败），若发生则回滚并把局面打进 console |
| 8 | `stats.moves++`（FR-22：只计成功入槽） | — |
| 9 | `tray.findTriple(tile.icon)` → 命中则取 3 个槽序号 | 未命中 → 跳步 12 |
| 10 | 3 张牌 `setState('cleared')`，从槽位移除（**不重排剩余槽位**，BR-03） | — |
| 11 | 补全命令的 `cleared` 字段（记录每张的原 slotIndex），`undo.push(cmd)` | — |
| 12 | `emit('tile:entered')`；若有消除再 `emit('tiles:cleared')`；`emit('board:changed')`、`tray:changed`、`stats:changed` | 事件顺序固定：先入槽后消除（动画要按这个顺序播） |
| 13 | Game 判终局：`board.size===0 && tray.size===0` → `Won`；`tray.isFull() && 本次未消除` → `Lost`（FR-13） | 两者互斥；同时成立不可能（清空则槽空） |
| 14 | `state.transition` 若变化 → `timer.stop()` → `emit('state:changed')` → 通关则 `repo.submitBest` + `repo.clearGame` | — |
| 15 | `repo.saveGame`（节流） | — |

**关于"三消连锁"**：第 9 步只检测**刚入槽的图标**，消除后**不再检测其他图标**。这不是偷懒，而是 BR-03 的必然结果：消除不产生新牌，槽里其他图标数量没变，不可能因为这次消除而凑齐 3 张。任何"连锁"实现在这里都是死代码。

**陷阱（P05 一定会踩的两个）**：

1. **第 6、7 步的原子性**：`remove` 成功但 `append` 失败（槽满）时必须回滚 `board.add(tile)`，否则这张牌会凭空消失。虽然第 4 步已排除，但"槽满仍能点"是重构时最容易破坏的假设，所以第 7 步保留回滚分支。
2. **第 12 步之前不能动 DOM**：动画要用"牌还在原位"的坐标做 FLIP。若 `remove` 时立刻删节点，动画会从 (0,0) 飞出来。正确做法是 `BoardView` 在 `tile:entered` 时才移除节点，并用 `getBoundingClientRect()` 取起点。

### 6.2 撤销（对应时序图 `04-时序图-撤销.puml`）

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | PropBar → `game.useProp('undo')` | |
| 2 | Game → `state.can('prop')`，`props.canUse('undo')`（次数 > 0、栈非空、非终局） | 任一不满足 → 返回 `{ok:false, reason}`，按钮置灰且给出提示文案 |
| 3 | `props.consume('undo')`；`undo.undo(ctx)` 弹出栈顶并执行 | `ctx` 由 Game 组装（含 board/tray/props） |
| 4 | 按命令类型分支（命令内部完成，Game 不 switch）： | |
| 4a | `EnterTrayCommand`：若有 `cleared` → 3 张按原 slotIndex 放回槽位、`state='tray'`；再把主牌从槽位移出 → `board.add` 回原位、`state='board'` | 顺序很重要：**先恢复消除的 3 张，再移出主牌**。反序会让槽位短暂出现 4 张同图标，若此时有副作用会误触发 |
| 4b | `RemoveCommand`：3 张从牌堆移除 → 回原槽位；若 `createdLayer` 且该层已空 → `board.maxLayer--` 并记录层已删 | 次数由命令自己 `props.refill('remove')` |
| 4c | `ShuffleCommand`：按 `before` 逐张恢复 `icon`；`props.refill('shuffle')` | |
| 5 | `stats.moves` **不变**（Q-05 默认：步数不回退；FR-22 只定义入槽计数） | 这是刻意的：撤销是"操作次数"的代价，不是"时间倒流" |
| 6 | 若局面原先已终局（理论上不可：终局后 `can('prop')` 为 false）→ 不处理 | 终局不可撤销（BR-09） |
| 7 | `emit` 全量刷新：`board:changed` / `tray:changed` / `props:changed` / `state:changed`（若从终局恢复则不会发生） | 撤销后必须做**全量重渲染**，不做增量：增量容易漏（例如原本被压暗的牌现在可点了） |
| 8 | `repo.saveGame` | |

**为什么不给"撤销"做撤销**（BR-06）：撤销后再撤销等价于"重做"，而重做需要 redo 栈。本项目不做 redo —— 一是需求未要求，二是 redo 与"步数不回退"叠加会产生"用 redo 刷步数"的漏洞（redo 是否计步？无论怎么定都不自然）。**不做**是最省事且语义干净的选择。

### 6.3 移出（FR-18 / BR-07）

| 步 | 动作 | 细节 |
|---|---|---|
| 1 | `props.canUse('remove')`：次数 > 0、槽位非空、非终局 | 槽位为空时按钮置灰（§8 E-02） |
| 2 | `tray.takeFirst(3)` 取最早的 3 张（按槽序，跳过 null） | 槽里只有 1～2 张时：**照取**，不足 3 张就移 1～2 张（需求未禁止；若禁止需改 FR-18，属待确认，按"允许"实现并记入 §10） |
| 3 | 找落点：`board.findFreeCells(board.maxLayer())` | 定义"空闲"：该层格位未被占用，**且**与所有更高层的牌不重叠（更高层若压着它，放上去就不可点，违反 BR-07"放回后立即可点击"） |
| 4 | 若空闲格位 ≥ 3 → 取前 3 个；若 1～2 个 → 先用剩余，其余走第 5 步 | |
| 5 | 若空闲格位不足 → `board.addOverflowLayer()` 新建层（`maxLayer + 1`），格位取 `(0,0)、(2,0)、(4,0)`（半格单位，层内不重叠） | 新层天然在最上，三张都立即可点 |
| 6 | 逐张 `board.add(tile)`（写索引 + 更新 coverCount），`state='board'` | 移出**不换图标、不改 group**（BR-05：只改位置） |
| 7 | 槽位补位：剩余牌前移（`Tray` 内部压实 null） | 与"消除不重排"（BR-03）不矛盾：移出是玩家主动操作，视觉上必须紧凑 |
| 8 | `props.consume('remove')`；构造 `RemoveCommand`（含 `createdLayer`）入栈 | |
| 9 | 自检：`#assertInvariants()`（每种图标计数不变、未消除总数 % 3 === 0） | 失败 → 回滚整个移出并 `console.error('INVARIANT_BREAK_AFTER_REMOVE')`（§8 E-05） |
| 10 | 发事件、存档、判终局（移出不改变牌数，不会通关，但可能让局面从"必败"变回"可继续"） | |

**落点规则的取舍**：不追求"放回它原来的位置"（玩家已经看不见原位置了），而是"放回最上层、立即可点"。这条的好处是**移出一定是"救急"而不是"换个地方继续卡"**；代价是牌堆会"往上长"，视觉上牌堆越来越厚（可接受，因为一关最多用 1～2 次）。

### 6.4 洗牌（FR-19 / BR-08）—— 用分组置换保住可解性

**问题**：BR-08 要求"只换图标、不改结构"，BR-12 要求"保证存在通关序列"。若完全随机重排图标，可能把唯一的一组三张拆散到互相遮挡的位置 —— 理论上仍可能可解，但玩家再也找不到；更糟的是，洗牌这个"救急"道具会让局面更绝望。

**本设计的解法（DD-06）**：按 `Tile.group` 做**整组置换**。

| 步 | 动作 | 细节 |
|---|---|---|
| 1 | `props.canUse('shuffle')`：次数 > 0、牌堆非空、非终局 | |
| 2 | `board.groupTiles()` → `Map<group, Tile[]>` | |
| 3 | 过滤出**完整组**：`tiles.length === 3` 且全部 `state === 'board'` | 部分已进槽 / 已消除的组**不参与置换** |
| 4 | 记录 `before: Map<tileId, icon>`（仅参与组） | 撤销用 |
| 5 | 对参与组做组级随机置换（Fisher–Yates 作用于"组 → 图标"的映射） | 若置换后图标分布与原来完全相同（概率极小但会发生），重抽一次 |
| 6 | 逐张写 `tile.icon = 置换后该组的图标` | 位置、层号、group 全部不变（BR-08） |
| 7 | 自检：每种图标计数不变、未消除总数 % 3 === 0、`board.canPick` 结果集不变 | 任一不符 → 用 `before` 回滚并报错（§8 E-05） |
| 8 | `props.consume('shuffle')`；`ShuffleCommand` 入栈 | |
| 9 | `emit('ui:shuffle-anim')` → 图标翻转动画 → 全量重渲染 | |
| 10 | 存档、判终局（洗牌不改变数量，不会直接触发终局） | |

**为什么整组置换能保住可解性**：可解序列 S 是"位置序列"，玩家按 S 点击即可清空。整组置换只改变"某组贴哪个图标"，不改变"哪些位置属于同一组"。按 S 点击时，第 3k+1 到 3k+3 个位置仍是同一组、仍是同一图标，第 3 张入槽即消除，槽位峰值仍为 3。**这是构造性的保证，不是概率性的**。

**为什么不参与不完整组**：若一组 3 张里已有 2 张在槽位（同为图标 X），剩下 1 张在牌堆，此时把这 1 张换成图标 Y，槽里那 2 张就永远凑不齐 —— 除非槽位里已有第 3 张 Y。这会把"可解"变成"看运气"，所以不完整组一律不动。

**与 BR-08"洗牌不得使局面变得更不可解"的关系**：整组置换不仅在存在性上保持可解，还**保持了"哪一段序列对应哪一组"的结构**，因此难度分布也不变 —— 玩家的失败只可能来自"没找到序列"，不会来自"洗牌把牌洗坏了"。

### 6.5 失败判定（FR-13 / BR-02）

| 步 | 动作 | 细节 |
|---|---|---|
| 1 | 触发点**只在**入槽之后（§6.1 第 13 步）；不在"点道具后"也检查 | 移出只会让槽位变空，不可能导致失败；洗牌不改变槽位 |
| 2 | 条件：`tray.size === 7` **且** 本次入槽未产生消除 | |
| 3 | 顺序：**先**完成消除结算（若有），**再**判失败 | 若先判失败，"第 7 张恰好凑成三消"会被误判为失败 |
| 4 | 失败后：`state → Lost`、`timer.stop()`、锁牌堆与道具、隐藏"撤销"（BR-09） | |
| 5 | 结算弹窗展示：结果、用时、步数、道具使用次数（FR-15） | |
| 6 | **不写最佳记录**（失败无记录，见 UC-05→UC-13 只有通关 include） | |
| 7 | 清存档（`repo.clearGame`），避免"刷新后回到已失败的局面" | 这一步容易漏：失败局面恢复后无法继续，只会让玩家困惑 |

**边界：槽位 7 张但有三消可消**。第 3 步的"先消除后判失败"直接排除了这种情形 —— 若第 7 张凑成三消，消除后槽位只剩 4 张，失败条件不成立。此时游戏继续，玩家获得一次"险胜"体验（这也是三消类游戏的一个爽点）。

## 7. 界面设计

### 7.1 尺寸基准：半格单元 `--u`

所有尺寸由一个 CSS 变量驱动，改一处即可整体缩放：

| 变量 | 值 | 推导 |
|---|---|---|
| `--u` | 28px | 半格单元（牌宽的一半） |
| `--tile` | 56px | 牌边长 = `2 × --u` |
| `--gap` | 8px | 槽位格间距 |
| `--slot` | 56px | 槽位格边长 = 牌边长 |

**为什么用"半格"而不是"格"**：层间错位是半张牌，若以整张牌为基准，偏移量会出现 0.5 这种非整数值，而覆盖判定要求整数（D-01）。把基准设为半格后，所有坐标都是整数，`overlaps` 退化为 `|Δcol| < 2 && |Δrow| < 2`。

### 7.2 区域划分

```
┌──────────────────────────────────────────────────────────┐
│ ① 顶部状态栏 (56px)                                       │
│   关卡名 │ 剩余牌数 │ 用时 mm:ss │ 步数 │ ⏸ 暂停          │
├──────────────────────────────────────────────────────────┤
│ ② 牌堆区（自适应，居中，内部舞台按关卡尺寸等比缩放）        │
│                                                          │
│              [层 2]  ■ ■ ■                                │
│           [层 1]  ■ ■ ■ ■                                 │
│        [层 0]  ■ ■ ■ ■ ■                                  │
│                                                          │
├──────────────────────────────────────────────────────────┤
│ ③ 槽位区 (56px + 上下留白 = 72px)                         │
│    [ ][ ][ ][ ][ ][ ][ ]   7 格                          │
├──────────────────────────────────────────────────────────┤
│ ④ 道具区 (64px)                                           │
│    ↺ 撤销×3      ⇧ 移出×2      ⇄ 洗牌×2                   │
└──────────────────────────────────────────────────────────┘
⑤ 弹窗层（覆盖整个视口，display:none 时不影响布局）
```

| 区域 | 实现要点 |
|---|---|
| ① 状态栏 | `position: sticky; top: 0`；数字用等宽字体（`font-variant-numeric: tabular-nums`），避免秒数跳动时宽度抖动 → 这是"计时显示跳动"的唯一正解 |
| ② 牌堆区 | 外层 `flex:1; overflow:hidden`；内层 `.stage` 固定像素尺寸（由关卡算出），用 `transform: scale(k)` 等比缩放，`k = min(1, 可用宽/stage宽, 可用高/stage高)` |
| ③ 槽位区 | 7 个固定格节点（不做增删），空格用虚线边框；每格内放牌节点或空 |
| ④ 道具区 | 3 个按钮，含角标（剩余次数）；`disabled` 时降不透明度并禁指针 |
| ⑤ 弹窗层 | 单个容器 + 4 种内容模板（结算/暂停/说明/重开确认），同一时刻只显示一个 |

### 7.3 牌的定位与层错位

```
left = (col × --u) + jitterX
top  = (row × --u) + jitterY
width: height: var(--tile)
z-index = 100 + layer × 10 + row     // 同层内按行号微调，保证绘制稳定
```

- 层错位已含在 `col/row` 里（`col = 2c + layer%2`），渲染层不再额外偏移 —— 否则会出现"判定与视觉错位"的经典 bug。
- `jitter` 只加到 `left/top`（视觉），**不写回模型**；`getBoundingClientRect()` 得到的坐标不参与任何判定。
- z-index 分两段：牌 100～999，弹窗 9000+，遮罩 8000+。牌的总数是 144，`100 + 8×10 + 3` 远小于 1000，不会越界到弹窗层。

### 7.4 点击热区

| 情形 | 行为 |
|---|---|
| 可点的牌 | 热区 = 整张牌（56×56），`cursor: pointer` |
| 被覆盖的牌 | **仍然保留热区**，点击给"抖动 + 提示音"（FR-11）；`cursor: not-allowed`，整体压暗 35% |
| 视觉重叠时谁先命中 | 由 `z-index` 决定（上层在上），与"被覆盖"判定一致；但**判定不由命中决定** —— 即使浏览器把点击给了上层牌，Game 仍会用 `canPick` 复核 |
| 动画期间 | `.stage.is-locked` 加 `pointer-events: none`（FR-10），同时 Game 内 `#locked` 也拒绝——两道保险，因为前者挡不住键盘/脚本触发 |

**热区与视觉不一致的处理**：牌有 9px 抖动，因此牌的实际绘制矩形与格位矩形最多差 9px。相邻牌的热区可能重叠 9px —— 这在实践中无感（用户点的是牌心），但要在 §8 记一条：若出现"点 A 却选中 B"，就改为按格位矩形做命中（`pointer-events: none` + 统一事件委托算最近格位）。

### 7.5 动画触发点

| 动画 | 触发事件 | 时长/曲线 | 说明 |
|---|---|---|---|
| 入槽飞行 | `tile:entered` | 220ms `cubic-bezier(.2,.8,.2,1)` | FLIP：起点取 `getBoundingClientRect()`，终点取槽格矩形；牌从牌堆节点"复制"一份飞行层，原节点在动画后删除 |
| 三消消除 | `tiles:cleared` | 260ms `ease-in` | `scale(1.15) → scale(0)` + `opacity: 1 → 0`，三张同时（错开 30ms 制造节奏） |
| 无效点击抖动 | `tile:rejected` | 120ms × 3 次 = 360ms | `translateX(±4px)`，只动被点的牌 |
| 洗牌翻面 | `ui:shuffle-anim` | 320ms | 参与置换的牌做 `rotateY(90deg) → 换图标 → rotateY(0)`，视觉上像翻牌 |
| 失败 | `state:changed → Lost` | 420ms | 遮罩淡入 + 牌堆整体下坠 8px 回弹 |
| 通关 | `state:changed → Won` | 600ms | 遮罩淡入 + 剩余槽位牌逐个淡出（若有） |

**动画与锁的关系**：`Animator` 的每个方法返回 Promise，`Renderer` 在动画开始时 `game.lock()`、结束时 `game.unlock()`。锁期间 `clickTile` 直接返回 `{ok:false, kind:'noop'}`，**不发出任何提示**（否则动画期间连点会疯狂抖动）。

**降低动效**：`settings.reduceMotion || matchMedia('(prefers-reduced-motion: reduce)')` 为真时，所有动画时长置 0 并立即 resolve；锁也随之立即解除。

| 编号 | 情形 | 设计处理 | 依据 |
|---|---|---|---|
| E-01 | 牌堆为空 | 不可能"只剩空牌堆"：牌堆空时槽位必有牌（否则已通关）；若两者都空 → 判通关 | FR-14 |
| E-02 | 槽位为空时点撤销 | `props.canUse('undo')` 返回 `{ok:false, reason:'empty-stack'}`（栈空，与槽位无关）；按钮置灰。**撤销不看槽位**，只看栈 | FR-17 |
| E-03 | 槽位为空时点移出 | `canUse` 返回 `reason:'tray-empty'`，按钮置灰 + 悬停提示"槽位为空" | FR-18 |

| E-05 | 洗牌后仍无解 | 设计上不可能（§6.4 构造性保证）。兜底：洗牌后自检失败 → 用 `before` 回滚图标 → 提示"洗牌失败，次数已返还" → 控制台报 `INVARIANT_BREAK_AFTER_SHUFFLE` | BR-05、BR-12 |

| E-07 | 存档损坏（JSON 解析失败 / 字段缺失 / 版本不符） | `Repository.loadGame` 返回 null → 清空该键 → 进入该关的初始局面 → 顶部 toast "存档已失效，已重新开始" | BR-11 |
| E-08 | localStorage 不可用（隐私模式 / 配额满） | `StorageAdapter.isAvailable()` 为 false 时降级为**内存存储**：游戏可玩，但刷新后丢档，界面提示一次"当前浏览器不支持本地存档" | BR-11、FR-25 |
| E-09 | 快速连点同一张牌 | 第 1 次点击后牌已移入槽位，第 2 次 `board.get(id)` 返回 undefined → `{ok:false, kind:'noop'}`，无提示无副作用 | FR-08 |
| E-10 | 动画期间点击 | §7.5 的双保险：CSS `pointer-events:none` + Game `#locked` | FR-10 |
| E-11 | 点击被覆盖的牌 | 抖动 + 提示音，**不增步数、不入撤销栈** | FR-11、FR-22 |
| E-12 | 暂停中切到后台再回来 | 计时用累计毫秒（§3.11），`visibilitychange` 隐藏时自动 `pause()`（避免"回来发现多算了 20 分钟"） | BR-10、FR-23 |
| E-13 | 结算弹窗期间点牌 | `state.isTerminal()` → 拒绝；牌堆加 `.is-locked` | BR-09 |
| E-14 | 移出时槽位不足 3 张 | 允许移出实际张数（1～3 张），状态栏提示"已移出 N 张"。这是需求未明确处，记入 §10 DQ-01 | FR-18 |
| E-15 | 溢出层用完后撤销 | `RemoveCommand.undo` 检查该层是否已空 → 空则删层并把 `maxLayer` 回退；非空（玩家又用了移出）则不删，只回退这 3 张 | BR-07 |
| E-16 | 连续两次移出都触发新建层 | 每次 `addOverflowLayer` 都 `maxLayer + 1`，两层并存；撤销按命令 LIFO 天然正确 | BR-07 |

## 9. 设计决策记录

> 每条都给出"备选方案"与"影响的代码范围"，便于 P06 出问题时回溯"当时为什么这么定"。

| 编号 | 决策项 | 备选方案 | 选择理由 | 影响范围 |
|---|---|---|---|---|
| DD-01 | 渲染用 **DOM 绝对定位** 还是 Canvas | ①DOM（选）②Canvas 2D ③Canvas + WebGL | ①原生点击热区与 `disabled`/`aria` 直接可用，无需自写命中测试；②CSS 动画与 `transition` 免费获得 FLIP；③144 个节点对浏览器是小菜（Canvas 的优势在万级对象）；④无构建工具、无第三方库的项目约束下，DOM 代码量约为 Canvas 的 1/3。代价：大量节点时重排开销，本项目不触发 | 表现层全部；模型层无感 |
