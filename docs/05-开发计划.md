## 1. 计划总览

### 1.1 计划的唯一硬指标

每一轮结束时，**打开 `index.html` 必须能看到上一轮没有的东西，并且能当场演示**。

这条指标是刻意的：它让"进度"变成可观察的事实，而不是"代码写了多少行"。因此每一轮都定义了 **"本轮结束你会看到什么"**，这句话是本轮交付的最低承诺，也是人工验收的第一眼判断依据。

### 1.2 时间预算

截止 **2026-11-02 23:59**，编制时点为 10-31 约 16:20，可用约 **55 小时**（含睡眠与报告写作）。

| 时段 | 安排 | 说明 |
|---|---|---|
| 10-31 晚 | 迭代 1、迭代 2 | 两轮都是纯前端骨架与交互，边界清楚 |
| 11-01 上午 | 迭代 3 | 生成器是本项目算法密度最高的一轮，单独占一个完整时段 |
| 11-01 下午 | 迭代 4 | 命令与道具，改动集中在 `src/model/commands.js` 与 `prop-manager.js` |
| 11-01 晚 | 迭代 5 | 持久化与设置，机械性工作为主 |
| 11-02 上午 | 迭代 6 + 全量回归 | 动画收尾、音效、求解器脚本、README |
| 11-02 下午 | P06 修复 + P07 走查 | 修回归里暴露的问题，做一次依赖与命名走查 |
| 11-02 晚 | P08/P09 报告 + P10 核对 + 截图 | 报告素材在每轮验收时已同步产出，此时只做组装 |

**缓冲**：全部 6 轮合计预估 26～32 小时有效工作，对 55 小时窗口留出约 40% 余量，用于 P06 返工与报告写作。若 11-01 结束时迭代 4 未通过，按 §8 的裁剪顺序处理，**不推迟报告**。

## 2. 迭代划分（迭代 1～6）

### 迭代 1：项目骨架 + 数据模型 + 静态牌堆

**目标**：页面能打开，能看到一个分层错位堆叠的牌堆（固定样例数据、占位图标），但还点不动。

**为什么这样切**：这一轮把"模型层能否支撑渲染"这件事先验证掉。牌堆是本项目唯一有真实几何关系的部分，如果 `Tile`/`Board`/坐标体系一开始就是错的，后面所有交互都会建在歪地基上。用固定样例而不是生成器，是为了让"几何对不对"不被"生成算法对不对"污染。

| 项 | 内容 |
|---|---|
| 覆盖需求 | FR-02（多层堆叠展示，暂不含 HUD 实时递减）、FR-03（关卡配置的读取）、FR-06（错位与抖动）、FR-01（仅入口占位） |
| 覆盖规则 | 无业务规则落地，仅涉及"每张牌四种属性"的数据约定 |
| 交付文件 | **新建** `nailegenai/index.html`、`nailegenai/styles/base.css`、`nailegenai/styles/layout.css`、`nailegenai/styles/board.css`、`nailegenai/src/model/tile.js`、`nailegenai/src/model/board.js`、`nailegenai/src/model/level-config.js`、`nailegenai/src/model/icon-set.js`、`nailegenai/src/engine/event-bus.js`、`nailegenai/src/view/board-view.js`、`nailegenai/src/view/renderer.js`、`nailegenai/src/main.js`、`nailegenai/src/data/fixture.js` |
| 禁止事项 | ①不写点击与任何交互；②不写 `Tray`、`Game` 的判定逻辑；③不写生成器与计时器；④不写 CSS 动画；⑤不写 localStorage；⑥不在渲染代码里硬编码层数/牌数（必须来自配置或 fixture） |
| 验收方式 | **AC-01**：打开页面并"进入入门关"，看到牌堆、牌有重叠、被压的牌压暗。<br>**AC-05**：同层牌有不超过 1/6 牌宽的随机偏移，且刷新后偏移变化但牌面结构不变。<br>**AC-03（部分）**：控制台打印 `board.debugCount()`，输出每层张数与总数，且与 fixture 声明一致。<br>**AC-04（部分）**：控制台调用 `assertInvariants()`，fixture 数据通过（总张数为 3 的倍数）。 |
| 本轮结束你会看到什么 | 一个居中的牌堆，三层以上、层间错位、上层压住下层并压暗下层；控制台两行输出：`layer0: 6, layer1: 4, layer2: 2, total: 12` 与 `invariants: OK` |
| 前置检查 | 见 §4.1 |
| 工作量控制 | 5 个纯模型文件 + 3 个视图/骨架文件，无算法；单文件不超过 120 行 |

**本轮的刻意省略**：`Board` 的 `occupied`/`coverCount` 两个派生索引**这一轮就要建**，因为它们是 `canPick` 的基础，延后会导致迭代 2 返工。但"压暗"只按 `coverCount > 0` 渲染，不实现点击拒绝。

### 迭代 2：交互核心（点击判定 → 入槽 → 三消 → 失败）

**目标**：能真正玩起来——点可点的牌、进槽、凑三消除、槽满判负。

**为什么在第 1 轮之后**：覆盖判定依赖第 1 轮建好的 `coverCount` 索引；入槽依赖第 1 轮的坐标系（动画终点要算到槽格）。这两件事都不能提前。

| 项 | 内容 |
|---|---|
| 覆盖需求 | FR-07（可点击判定）、FR-08（点击入槽）、FR-09（三消消除）、FR-10（消除动画与连消反馈，仅"动画期间忽略点击"这一半）、FR-11（无效点击反馈）、FR-12（槽位展示）、FR-13（失败判定） |
| 覆盖规则 | BR-01（覆盖判定：被压即不可点）、BR-02（槽位容量 7）、BR-03（三消即时性：只测刚入槽的图标、消除后不重排）、BR-04（数量不变量在"入槽 + 消除"后仍成立，本轮先建断言、第 3 轮才真正受生成器约束） |
| 交付文件 | **新建** `nailegenai/src/model/tray.js`、`nailegenai/src/view/tray-view.js`、`nailegenai/src/view/animator.js`、`nailegenai/styles/tray.css`、`nailegenai/styles/animations.css`、`nailegenai/src/engine/game.js`、`nailegenai/src/engine/game-state.js`；**修改** `board-view.js`（可点性热区与压暗）、`renderer.js`（分派子视图）、`main.js`（绑定点击） |
| 禁止事项 | ①`Tray` 里不出现"玩家输了"这种结论（只返回 `{isFull, hasTriple}` 事实）；②覆盖判定不得使用 `getBoundingClientRect`；③失败不能写成"点满 7 次"；④不做道具、不做计时、不做关卡切换、不做存档；⑤动画不得改变模型数据（`jitter` 不进坐标） |
| 验收方式 | **AC-06**：点被压住的牌，牌抖动、不入槽、步数不变。<br>**AC-07**：点完全露出的顶层牌，入槽并在槽格内显示。<br>**AC-08**：连点三张不同图标，槽内从左到右按点击顺序排列，第 3 张插在末尾。<br>**AC-09 / AC-10**：凑成 3 张同图标时立即消除，剩余牌保持原顺序。<br>**AC-11**：消除动画期间连点其他牌，全部被忽略，且没有二次入槽。<br>**AC-12**：连续点被压住的牌 3 次，每 3 次抖动一轮，槽位与步数均不变。<br>**AC-13 / AC-14**：7 张互不同图标→判负并锁定；第 7 张恰好三消→不判负。 |
| 本轮结束你会看到什么 | 一套能玩到输的完整交互：牌飞进槽位、凑三消失、槽满后界面锁死并提示"槽位已满" |
| 前置检查 | 见 §4.2 |
| 工作量控制 | `game.js` 是本轮唯一的大文件（≤ 220 行），其余均 ≤ 120 行 |

**本轮埋下的技术改造点（迭代 4 会动）**：本轮 `Game.clickTile()` 内部**直接**改模型（`board.remove` → `tray.append` → `tray.findTriple` → 判负）。迭代 4 引入命令层时，把这段实现整体搬进 `EnterTrayCommand.execute(ctx)`，**`clickTile` 的签名与返回结构保持不变**。这条约定写在这里，是为了让那次重构是"计划内的一次替换"，而不是"推倒重来"。

### 迭代 3：关卡与生成器（三难度 + 通关 + 计时步数）

**目标**：三个难度都能开、都能通关，牌数正确，牌堆清空即通关，计时与步数准确。

**为什么放在第 2 轮之后**：生成器需要"什么是合法牌堆"的判据（每种图标 3 的倍数、层间覆盖关系），而这两条判据在第 2 轮已经用 fixture 验证过一遍。先生成器再交互，就会在"牌堆本身对不对"还没验证时引入第二组变量。

| 项 | 内容 |
|---|---|
| 覆盖需求 | FR-01（完整：三关入口、进入、显示是否通关）、FR-03（三关参数差异）、FR-04（生成与数量不变量）、FR-14（通关判定）、FR-15（结算界面，本轮只做结果/用时/步数/道具数 + 返回选关）、FR-21（计时）、FR-22（步数）、FR-02（HUD 剩余牌数实时递减） |
| 覆盖规则 | FR-14 的通关判据（纯事实：牌堆与槽位皆空）、BR-04（数量不变量由生成器自检保证）、BR-12（可解性保证，构造性）、FR-02 的剩余牌数口径（牌堆未消除 + 槽位中） |
| 交付文件 | **新建** `nailegenai/src/engine/level-generator.js`、`nailegenai/src/engine/tile-factory.js`、`nailegenai/src/engine/strategies/layout-strategy.js`、`nailegenai/src/engine/timer.js`、`nailegenai/src/view/hud-view.js`、`nailegenai/src/view/dialog-view.js`、`nailegenai/styles/dialog.css`、`nailegenai/src/data/levels.js`；**修改** `game.js`（`startLevel`/结算）、`game-state.js`（加 `Won`/`Ready`）、`renderer.js`、`main.js`；**删除** `src/data/fixture.js`（改由生成器产出） |
| 禁止事项 | ①生成器不得把图标随机撒（必须按"可解序列反向铺牌"，否则 BR-12 无法保证）；②计时不得用 `setInterval` 每秒累加（会漂移，见 §5 R-07）；③结算不得复用 `Playing` 状态下的点击链路；④不做道具、不做暂停、不做存档、不做最佳记录；⑤`hud-view` 不做倒计时（本项目只有正计时） |
| 验收方式 | **AC-02**：分别点三关都能进入且无报错。<br>**AC-03**：三关总牌数分别为 60 / 108 / 144，且分别是 3 的倍数。<br>**AC-04**：生成后控制台 `assertInvariants()` 全部通过，故意破坏一张图标后断言报错。<br>**AC-15**：清空牌堆全部牌，立即弹结算并显示"通关"。<br>**AC-16 / AC-17**：失败与通关共用结算弹窗，字段齐全（结果/用时/步数/道具次数）。<br>**AC-25**：进关等 10 秒，显示 00:10；再等 5 秒显示 00:15。<br>**AC-26**：点 5 张可点牌 + 2 张被压牌，步数为 5。<br>**AC-34**：HUD 剩余牌数随消除实时递减，且等于"牌堆未消除 + 槽位中"。 |
| 本轮结束你会看到什么 | 选关界面三张卡片（显示 4/6/9 层与 60/108/144 张），难度真的不同；清空后弹结算，显示用时与步数 |
| 前置检查 | 见 §4.3 |
| 工作量控制 | `level-generator.js` ≤ 200 行（含注释解释"为什么反向铺牌"），`layout-strategy.js` ≤ 120 行 |

**本轮必须做对的"一件小事"**：`assertInvariants()` 要能被控制台直接调用，并返回**可读报告**（哪条不变式失败、期望值、实际值），而不是抛一个裸 `throw`。这条在第 2 轮的 `canPick` 边界验证里已经用过一次同样手法，属于本项目的固定验证方式。

### 迭代 4：道具（撤销 / 移出 / 洗牌 + 次数管理 + 不变量校验）

**目标**：三种道具都能用、次数有限、用错能撤销，且任何操作后"每种图标张数 % 3 == 0"仍然成立。

| 项 | 内容 |
|---|---|
| 覆盖需求 | FR-16（道具栏与次数）、FR-17（撤销，含归还次数与上限 30）、FR-18（移出 3 张到最上层）、FR-19（洗牌只换图标）、FR-20（次数管理与耗尽提示） |
| 覆盖规则 | BR-05（道具不破坏不变量）、BR-06（撤销语义：回退操作并归还次数）、BR-07（移出落点规则：最上层可点位置）、BR-08（洗牌只换图标、不动位置）、BR-09（终局锁定：道具不可用）、BR-13（道具次数来自配置） |
| 交付文件 | **新建** `nailegenai/src/model/command.js`、`nailegenai/src/model/commands.js`、`nailegenai/src/engine/undo-manager.js`、`nailegenai/src/engine/prop-manager.js`、`nailegenai/src/engine/strategies/shuffle-strategy.js`；**修改** `game.js`（`clickTile` 改为走命令、新增 `useProp`）、`hud-view.js`（道具区三个按钮）、`board-view.js`（洗牌翻面与溢出层渲染）、`animations.css`（洗牌翻面） |

| 前置检查 | 见 §4.4 |
| 工作量控制 | `commands.js`（5 个命令）≤ 260 行，是本项目单文件最长的；`shuffle-strategy.js` ≤ 80 行 |

**本轮的风险最高处**：AC-23 是"道具 × 撤销"的组合场景，也是唯一能暴露"命令存了对象引用"的验收项。这条要格外认真地手工走两遍。

### 迭代 5：持久化与设置（存档 / 最佳记录 / 暂停 / 重开 / 设置项）

**目标**：关掉页面再打开，能回到原来的对局；暂停真的停；结算显示最佳记录；设置项刷新后仍生效。

| 代码 | 只改"交付文件清单"里的文件，中文注释写"为什么" |
| 改动清单 | 文件 → 做了什么（一句话），便于你 diff 时定位 |

| 已知未完成 | 本轮刻意省略的东西，以及它属于哪一轮 |

### 6.4 通过/不通过的分级

| 级别 | 判据 | 处理 |
|---|---|---|
| **通过** | 该轮全部 AC 通过，控制台无报错 | 进入下一轮 |
| **有条件通过** | 主体可用，个别 P1 级体验问题 | 记入缺陷清单，**不阻塞**下一轮，放到 P06 统一修 |
| **不通过** | 任一 P0 AC 失败（判定错、无法通关、数据被改坏） | 立即发 P06，修完复验，**不进入下一轮** |

> 判据的用意：把"能继续往下做"和"必须停下修"分开。装饰性缺陷不该打断迭代节奏，正确性缺陷必须当场停。

## 8. 裁剪规则与变更控制

### 8.1 时间不足时的裁剪顺序（从先砍到后砍）

| 顺序 | 裁什么 | 为什么可以砍 | 影响 |
|---|---|---|---|
| 1 | 迭代 6 的音效 | 不影响任何 FR 的判定，只是体验 | FR-26 只保留"设置项存在"，标题写"音效（本期未实现）" |
| 2 | 迭代 6 的洗牌翻面/失败下坠/通关淡出动画 | 只影响观感 | FR-10 保留"入槽飞行 + 三消缩放"两个核心 |
| 3 | 迭代 5 的最佳记录 | 属"记录"类需求，砍掉不影响可玩性 | FR-24 标为未实现；**但存档必须保留** |
| 4 | 迭代 4 的洗牌 | 三种道具里唯一"锦上添花"的 | FR-19 标为未实现，`props.shuffle` 置 0 次 |
| 5 | 迭代 5 的设置弹窗（只留音效开关一行） | 玩法说明可以写进页面底部 | FR-26 简化 |
| **不砍** | 判定、生成器、存档、撤销、移出、计时 | 这些是 P0，砍了就不是这个游戏 | — |

### 8.2 变更控制

- **允许在迭代中调整**：实现细节、文件内部拆分、注释措辞。
- **必须停下来问**：任何涉及"需求含义"的改动（例如想把"移出 3 张"改成"移出 1 张"）、任何新增需求、任何要动 `docs/02`～`04` 已冻结结论的改动。
- **处理方式**：不擅自改，记入 `07-AI交互记录.md` 的"待确认"，等人工裁定后再改文档、升版本号。

### 8.3 每轮结束的强制自检（我这边做，再交给你）

1. 文件是否只在清单内？
2. 是否有 `console.log` 遗留在非调试入口？
3. 模型层是否 import 了视图层（DEP-1/DEP-2 反查）？
4. 是否引入了第三方依赖或外部网络资源（NFR-01）？
5. 本轮"你会看到什么"这句话，自己先验证一遍成立。
