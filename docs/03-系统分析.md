## 1. 候选对象识别

### 1.1 识别方法

从需求文档 v1.1 中抽取**名词**（候选实体）与**动词**（候选行为），再用三条准则筛选。刻意不做"一步到位"的抽象：先把候选摊开，再逐条判死，这样报告里能看清"为什么不是对象"。

**筛选准则**

| 准则 | 含义 | 不满足则 |
|---|---|---|
| C1 有状态 | 在生命周期内会变化，且变化需要被记住 | 纯动作 → 变成某对象的方法 |
| C2 有身份 | 同类实例之间需要被区分（有 id 或独立生命周期） | 纯数据 → 变成属性或值对象 |
| C3 有独立变化轴 | 它的变化原因与其他对象不同（单一职责） | 合并到相邻对象 |

### 1.2 名词扫描与去留

| 序号 | 候选（来自需求） | 判定 | 理由 |
|---|---|---|---|
| 1 | 牌 Tile | **保留（实体）** | 有身份（同一张牌在牌堆与槽位间移动）、有状态（在牌堆/槽位/已消除）、位置随移动改变 |
| 2 | 牌堆 Board | **保留（实体·聚合根）** | 持有牌集合并拥有"覆盖关系"这一全局性质；覆盖判定无法由单张牌完成（C3：它的变化原因是"牌的位置结构"，与牌的"图标身份"不同） |
| 3 | 层 Layer | 淘汰 | 无身份、无独立行为，只是 Board 内索引的一个维度（C2 不满足） |
| 4 | 格位 / 坐标 Cell | 淘汰为**值对象** | 两个坐标相等即相同，无身份可言；作为 Tile 的位置属性存在 |
| 5 | 图标 Icon | 淘汰为**值对象** | 图标是"字符/颜色"的不可变组合，无独立生命周期 |
| 6 | 图标库 IconSet | **保留（实体·只读集合）** | 它回答问题"本关允许哪几种图标"，是生成期的配置来源，独立于任何一张牌 |
| 7 | 牌工厂 TileFactory | **保留（创建者）** | 创建 Tile 需要统一分配 id 与绑定图标；若散落在生成器里，id 唯一性无处保证 |
| 8 | 关卡 Level | 淘汰（与 9 合并） | "关卡"在需求中同时指"静态配置"与"一次游玩"，二者混名会造成二义；游玩过程归 Game，静态参数归 LevelConfig |
| 9 | 关卡配置 LevelConfig | **保留（值对象·不可变）** | 承载层数/张数/图标种类/道具次数，并被生成器、道具、结算多处读取；不可变，避免运行期被改 |
| 10 | 关卡生成器 LevelGenerator | **保留（创建者）** | 承担"如何排布才保证可解"这一独立难题，明显不是任何实体的职责 |
| 11 | 槽位 Tray | **保留（实体）** | 持有**有序**序列（顺序即语义）、有容量上限、是三消判定的发生地 |
| 12 | 三消组（Triple） | 淘汰为**值对象** | 只是"同图标的三张牌"这一查询结果，随用随弃 |
| 13 | 道具 Prop | 淘汰（拆解） | "道具"是三样东西的合称：次数与准入（→ PropManager）、效果（→ Board / Tray 的操作）、可逆性（→ Command）。强行做成一个 Prop 类会得到只有一个 `if` 的上帝对象 |
| 14 | 撤销 Undo | **保留为 UndoManager（控制者）** | 撤销栈有状态（栈内容）、有上限、有可用性判定 |
| 15 | 撤销栈 | 淘汰 | 是 UndoManager 的内部结构，不是独立对象 |
| 16 | 洗牌 Shuffle | 淘汰为**命令** ShuffleCommand | 洗牌是一次"可逆的操作"，其身份体现在命令里（要记住旧图标映射才能撤销），而不是一个长期存在的对象 |
| 17 | 移出 Remove | 淘汰为**命令** RemoveCommand | 同上；效果由 Board/Tray 提供，命令只记录"移了哪三张、原来在哪" |
| 18 | 计时 Timer | **保留（服务）** | 有状态（累计毫秒、运行/暂停）、被多处以不同节奏读取 |
| 19 | 步数 Steps | 淘汰为**字段**（挂在 Game 的对局统计上） | 纯计数，无行为。**注意**：需求把步数统计挂在 R-04 计时器角色下，分析认为步数不是时间量，列入遗留问题 P-01 |
| 20 | 最佳记录 Record | 淘汰为**值对象** | 三条数字（时间/步数/通关次数），由 Repository 存取 |
| 21 | 存档 SaveGame | 淘汰为**值对象（DTO）** | 只是"落盘形态"，不含行为；重建对象是各实体自己的事 |
| 22 | 设置 Settings | 淘汰为**值对象** | 两个布尔开关 |
| 23 | 结算结果 Result | 淘汰为**值对象** | 一次性传给弹窗的数据包 |
| 24 | 游戏 Game | **保留（控制者）** | 编排一局的生命周期、把玩家意图翻译成模型调用、据模型返回的"事实"下"胜负"结论 |
| 25 | 游戏状态 GameState | **保留（状态对象）** | 它的存在价值是把"现在允许做什么"这件事集中到一处；若用 4 个布尔标志（isPaused / isOver / isWon …）必然出现非法组合 |
| 26 | 玩家 Player | 淘汰 | 单机游戏里玩家不是被建模的对象，只是事件来源（C1 不满足：程序不需要记住玩家的任何状态） |
| 27 | 按钮 / 弹窗 / 遮罩 / HUD | 淘汰（界面控件） | 属于表现层内部结构，不做领域建模；否则模型会依赖 DOM |
| 28 | 动画 Animation | 淘汰为**辅助对象 AnimationPlayer** | 动画是"播放顺序"问题，与游戏规则无关 |
| 29 | 音效 Sound | 淘汰为**辅助对象 SoundPlayer** | 音效是副作用，规则不应依赖它（关闭音效不影响任何判定） |
| 30 | 视图 Renderer | **保留（边界对象）** | 它承担两件不可回避的事：把模型画出来、把像素点击翻译成 tileId |
| 31 | 存档库 Repository | **保留（服务）** | 序列化 + 版本校验 + 损坏容错，三件事都不属于任何实体 |
| 32 | 覆盖关系 Coverage | 淘汰 | 它是"牌堆的结构性质"，用 Board 的判定方法 + 占用索引表达，不需要独立对象 |
| 33 | 可解性 Solvability | 淘汰（约束 + 测试工件） | 运行时它是 LevelGenerator 的构造约束；验收时它需要一个**离线求解器**，那是测试工具，不进运行时 |
| 34 | 求解器 Solver | **不进运行时**（测试辅助） | 只在 AC-33 的验证中使用，避免为测试污染产品代码 |

### 1.3 动词扫描与归属

| 动词（需求中的行为） | 归属 | 说明 |
|---|---|---|
| 生成牌堆 | LevelGenerator | 一次性、有算法难度 |
| 判定可否点击 | Board | 依赖全局结构 |
| 点击（玩家意图） | Game（作为意图入口方法） | 不建成 ClickHandler 对象：它没有状态 |
| 入槽 | Tray.append + EnterTrayCommand | 效果在 Tray，可逆性在命令 |
| 检测三消 / 消除 | Tray | 三张是否同图标只有槽位知道 |
| 判负 / 判胜 | Game（读 Tray 报的事实） | 见 3.3 的分工原则 |
| 撤销 | UndoManager + Command | 栈在管理器，逆操作在命令 |
| 移出 / 洗牌的效果 | Board / Tray | 道具管理器只做准入 |
| 计时 / 暂停 | Timer + GameState | 时间在 Timer，能否暂停在状态 |
| 保存 / 恢复 | Repository | 含版本与容错 |
| 渲染 / 映射点击 | Renderer | 唯一允许碰 DOM 的对象 |

### 1.4 候选结果

**核心对象 14 个**（后续全部进入类图）：

| 分组 | 对象 | 类别 |
|---|---|---|
| 实体 | Tile、Board、Tray、IconSet | 有身份、有生命周期 |
| 创建者 | TileFactory、LevelGenerator | 负责"造"，不负责"用" |
| 值对象 | LevelConfig | 不可变配置 |
| 控制者 | Game、GameState、UndoManager、PropManager | 编排与状态 |
| 命令 | Command（抽象）+ 3 个具体命令 | 可逆操作 |
| 服务 | Timer、Repository | 无领域身份，提供能力 |
| 边界 | Renderer（含 SoundPlayer、AnimationPlayer 两个辅助） | 与外界交互的唯一出口 |

**被淘汰的不是"不重要"，而是"不该是对象"**：层与格位成了 Board 的索引，三消组成了查询结果，洗牌/移出成了命令，玩家与按钮留在了界面层。这套划分的检验标准只有一个——**改需求时只改一处**：换图标只改 IconSet，加关卡只改 LevelConfig，改判定只改 Board，改界面只改 Renderer。

## 2. 核心对象职责

每个对象给出三栏：**职责**（做什么）、**边界**（明确不做什么）、**协作**（与谁来往）。"边界"比"职责"更重要：职责重叠是耦合的起点，而耦合是撤销功能做不干净的直接原因。

### 2.1 Tile（牌）

| 项 | 内容 |
|---|---|
| 职责 | 持有自己的**身份**（id）、**图标**、**位置**（层号 + 格位 + 视觉抖动偏移）、**所处区域**（牌堆 / 槽位 / 已消除）；对外提供"我原来在哪"以便撤销 |
| 边界 | ① **不判定自己能否被点击**——可点击性是牌堆的全局性质，牌若自判就必须知道整堆，耦合方向反了；② 不负责把自己从容器里移除（容器的增删只能由容器做）；③ 不渲染、不知道像素 |
| 协作 | 被 Board 与 Tray 持有；被 Board 读取位置做覆盖判定；被 Renderer 读取以绘制；被 Command 记录为逆操作目标 |
| 为什么这样切 | 牌是唯一"会在两个容器之间搬家"的对象，所以"我在哪"必须由它自己记，否则撤销时无处查询原位置 |

### 2.2 Board（牌堆）

| 项 | 内容 |
|---|---|
| 职责 | ① 持有牌堆内的全部牌；② 维护**占用索引**（层 × 格位 → 牌），使覆盖查询不必遍历全堆；③ 提供覆盖判定 `canPick`；④ 提供"最上层空闲格位"查询（供移出道具）；⑤ 统计剩余牌数；⑥ 允许按原位置放回一张牌（撤销用） |
| 边界 | ① 不做三消（那是 Tray 的事）；② 不判胜负（那是 Game 的事）；③ 不压撤销栈（UndoManager 的事）；④ **不碰 DOM、不读坐标像素**；⑤ 不知道有"关"这回事，也不知道道具 |
| 协作 | 持有 Tile；被 LevelGenerator 填充；与 Tray 之间由 Game 编排着"交出一张牌"；被 Renderer 读取；被 PropManager 调用"取最上层空闲格位" |
| 为什么这样切 | 覆盖关系是**堆的结构性质**，只有"看得见全堆"的对象才能判；同时它不该知道"消掉三张会赢"，否则它就得依赖 Tray 与 Game |

### 2.3 Tray（槽位）

| 项 | 内容 |
|---|---|
| 职责 | ① 有序持有最多 7 张牌；② 追加一张（入槽）；③ 检测同图标是否达到 3 张；④ 移除那 3 张；⑤ **报告结构事实**：是否已满、是否存在可消组、是否溢出 |
| 边界 | ① 不判胜负——它只说"我满了且没有可消组"，"这局输了"由 Game 下结论；② 不判定覆盖；③ 不修改牌的图标；④ 不负责重排剩余牌以外的任何顺序问题 |
| 协作 | 持有 Tile；被 Game 调用；被 PropManager 取"最早的 3 张"（移出）；被 Command 记录消除快照 |
| 为什么这样切 | 见 3.3：**模型报事实，Game 下结论**。若 Tray 直接调 `game.lose()`，槽位与流程就形成双向依赖，撤销时无法判断"这一步是否曾导致终局" |

### 2.4 IconSet（图标库）

| 项 | 内容 |
|---|---|
| 职责 | 提供全部图标的定义（标识 + 字符/颜色）；按关卡配置取前 N 种；保证定义不重复、不缺字段 |
| 边界 | 不管每种发几张、不管发给谁、不参与布局 |
| 协作 | 被 LevelGenerator 读取（取 N 种）；被 Renderer 读取（画图标） |
| 为什么这样切 | NFR-05 要求"加图标只改一处"，如果不独立，图标就会散落在生成器的常量里 |

### 2.5 TileFactory（牌工厂）

| 项 | 内容 |
|---|---|
| 职责 | 创建一张 Tile：分配**全局唯一 id**、绑定图标、写入位置与抖动偏移 |
| 边界 | 不决定牌的**数量**、不决定**布局**、不做可解性构造——那是 LevelGenerator 的职责 |
| 协作 | 被 LevelGenerator 调用；使用 IconSet 中的图标定义 |
| 为什么这样切 | id 唯一性需要"一个地方统一发号"。若让生成器直接 `new`，一旦生成器重试（自检失败重来），id 就可能重复，而 id 是撤销与存档的定位依据，重复即灾难 |

### 2.6 LevelConfig（关卡配置）

| 项 | 内容 |
|---|---|
| 职责 | 承载单关的全部静态参数：层数、每层行列、图标种类数、每种张数、总牌数、道具次数；提供**自校验**（每种张数 % 3 == 0、总牌数 = 种类 × 每种、层容量足够放牌） |
| 边界 | 不含任何运行时状态（当前剩几张、用了几次道具都不在这里）；**不可变**，运行期不允许被修改 |
| 协作 | 被 LevelGenerator 读取以生成；被 Game 读取以初始化道具次数；被结算读取以显示关卡名 |
| 为什么这样切 | 自校验放在配置里，等于把 BR-04 的"3 的倍数"约束前移到"配置加载即报错"，而不是等开局玩到一半才发现消不完 |

### 2.7 LevelGenerator（关卡生成器）

| 项 | 内容 |
|---|---|
| 职责 | 按配置生成一整堆牌：计算每层格位 → **按可解序列反向铺牌**（保证 BR-12）→ 用 TileFactory 造牌 → 填入 Board → 做不变量自检，失败则重试（有限次数，超限报错而非静默死循环） |
| 边界 | 不渲染、不存档、不改配置；**不在运行时被反复调用**（只在开局与重开时） |
| 协作 | 依赖 LevelConfig、IconSet、TileFactory；产出交给 Board |
| 为什么这样切 | "怎么排才保证有解"是本项目**唯一有算法难度**的部分，把它隔离出来，才能独立验证（AC-33）而不牵动其他对象 |

### 2.8 Game（游戏流程）

| 项 | 内容 |
|---|---|
| 职责 | ① 编排一局的生命周期：开始 / 暂停 / 继续 / 重开 / 终局；② 接收玩家意图（点牌、用道具、撤销、暂停、重开）并**校验状态**；③ 调用模型完成状态变更；④ 依据模型返回的事实切换 GameState；⑤ 终局时组织结算数据、触发记录更新与存档；⑥ 持有对局统计（步数、道具使用次数） |
| 边界 | ① 不实现判定规则（覆盖归 Board、三消归 Tray）；② 不压栈（UndoManager）；③ 不实现道具效果（Board/Tray）；④ 不直接读写 localStorage（Repository）；⑤ **不引用 Renderer 的具体类**——通过"状态变化通知"让视图自己来取 |
| 协作 | 组合 Board、Tray、GameState、Timer、UndoManager、PropManager；依赖 LevelGenerator、Repository；被 Renderer 单向调用 |
| 为什么这样切 | Game 是**唯一知道"完整流程"的对象**，但它必须什么规则都不懂，否则它会变成第二个 Board + 第二个 Tray。它的价值在"次序"：先消再判负（AC-14 就靠这个次序） |

### 2.9 GameState（游戏状态）

| 项 | 内容 |
|---|---|
| 职责 | 持有当前状态（Idle / Ready / Playing / Paused / Won / Lost）；维护**合法迁移表**；回答"当前是否允许点击 / 道具 / 撤销 / 暂停" |
| 边界 | 不持有牌堆、不做业务判定、不渲染；**只有 Game 能迁移它**，其他对象只读 |
| 协作 | 被 Game 迁移；被 Renderer 读取（决定按钮禁用、遮罩）；被 UndoManager / PropManager 查询可用性 |
| 为什么这样切 | 六个状态若用布尔组合表示（是否暂停、是否结束、是否胜利）会产生 2³=8 种组合，其中 5 种是非法态；用单一状态值 + 迁移表可以把非法态**消灭在类型层面** |

### 2.10 Command（命令）与三个具体命令

| 项 | 内容 |
|---|---|
| 职责 | 抽象命令定义"这是一次可逆操作"，对外只暴露两件事：**这是什么操作**（用于归还道具次数）、**如何撤销**。三个具体命令各自记录撤销所需的全部信息：<br>· EnterTrayCommand：入槽的牌 + 它的原层原格位 + 本次是否触发了消除、被消的是哪 3 张（含它们在槽位中的位置）<br>· RemoveCommand：被移出的 3 张牌 + 它们原来的槽位位置 + 它们落在牌堆的哪个位置<br>· ShuffleCommand：洗牌前的完整"牌 → 图标"映射 |
| 边界 | 不决定何时执行、不压栈、不修改次数（次数归 PropManager）、不判终局 |
| 协作 | 被 UndoManager 持有；撤销时操作 Board / Tray；被 Game 创建 |
| 为什么这样切 | "能否精确撤销"完全取决于命令记了什么。特别是 EnterTrayCommand 必须记下"这次入槽顺带消了哪三张"——否则撤销时会变成"牌回到牌堆，但那三张同图标牌凭空消失"，这是这类游戏最典型的撤销 bug |

### 2.11 UndoManager（撤销栈）

| 项 | 内容 |
|---|---|
| 职责 | 压栈、取栈顶、弹栈、清空；维护上限 30（超出丢最旧）；回答"现在能否撤销"（栈非空 + 撤销次数 > 0 + 状态允许） |
| 边界 | ① **不实现逆操作**（命令自己会撤销）；② 不修改道具次数、不回退步数；③ 不持久化（刷新后从空栈开始，见需求第 9 章） |
| 协作 | 持有 Command；被 Game 调用；被 PropManager 查询 |
| 为什么这样切 | 栈的语义是"顺序 + 容量"，与"某一步具体怎么撤"是两件事。混在一起会导致每加一种操作就要改管理器 |

### 2.12 PropManager（道具管理器）

| 项 | 内容 |
|---|---|
| 职责 | ① 持有三种道具的剩余次数（初值来自 LevelConfig）；② **准入校验**（次数 > 0 + 状态允许 + 该道具在当前局面有意义）；③ 扣减与归还；④ 生成对应的 Command 交给 Game 入栈；⑤ 触发"次数已用完"的提示 |
| 边界 | ① **不实现道具效果**——移出的落点由 Board 算，洗牌的置换由 Board 执行；② 不判终局；③ 不直接改 UI（只报告，由 Renderer 渲染置灰） |
| 协作 | 依赖 Board、Tray（执行效果）；依赖 UndoManager（命令入栈）；依赖 GameState（可用性）；被 Game 调用 |
| 为什么这样切 | 道具的**共同点只有"有次数、可准入、可撤销"**，效果彼此毫无关系。把效果也塞进来，这个类会同时依赖牌堆布局算法与洗牌算法，成为最难改的地方 |

### 2.13 Timer（计时器）

| 项 | 内容 |
|---|---|
| 职责 | 累计毫秒；启动 / 暂停 / 继续 / 停止；格式化 mm:ss 供显示；保证暂停期间不累加、恢复后不跳变（BR-10） |
| 边界 | ① **不计步数**（见遗留问题 P-01）；② 不判断"是否超时"（本游戏无时限）；③ 不存盘（Repository 来取值） |
| 协作 | 被 Game 控制；被 Renderer 每秒读取；被 Repository 取值 |
| 为什么这样切 | 用"累计毫秒 + 上次恢复时刻"表达，而不是"每秒 +1"——后者在暂停、切后台、掉帧时一定会漂移（BR-10 的技术根据） |

### 2.14 Repository（存档）

| 项 | 内容 |
|---|---|
| 职责 | ① 把对局、记录、设置序列化为纯数据；② 反序列化并做**版本校验**与**结构完整性校验**；③ 读写 localStorage；④ 损坏时降级（不白屏、提示并重置） |
| 边界 | ① **不重建对象实例**（只产出纯数据；重建由 Tile / Board / Tray 各自的恢复入口完成）；② 不解释业务规则；③ 不决定何时存（Game 决定时机） |
| 协作 | 依赖 Board、Tray、Timer、PropManager、GameState 提供的快照；被 Game 调用 |
| 为什么这样切 | 若 Repository 直接 `JSON.parse` 后 `new Board(...)`，它就必须知道所有类的构造细节与顺序，版本升级时这里是唯一的爆炸点。让它只做"数据搬运"，类的恢复逻辑留在类自己身上（NFR-06 分层要求） |

### 2.15 Renderer（视图 / 边界对象）

| 项 | 内容 |
|---|---|
| 职责 | ① 把模型状态渲染为 DOM（牌堆、槽位、HUD、弹窗、遮罩）；② 把像素点击**映射为 tileId** 并转发给 Game；③ 播放动画与音效；④ 依据 GameState 置灰按钮、加遮罩 |
| 边界 | ① **不判定能否点击**（只负责"点到了哪张牌"）；② 不修改模型（只能调 Game 的意图入口）；③ 不读写 localStorage；④ 不做任何业务判断（包括"点了三张同图标该怎么办"） |
| 协作 | 单向依赖 Game（转发意图）、Board / Tray / GameState（只读状态）；使用 SoundPlayer、AnimationPlayer |
| 为什么这样切 | 划分法则是"**能否被替换**"：把 DOM 换成 Canvas，只要 Renderer 重写，其余 13 个对象一行不动。这就是 NFR-06 与 NFR-08 的落地方式 |

## 3. 对象关系分析

### 3.1 关系总表

| 起点 | 终点 | 关系 | 多重性 | 存在理由 |
|---|---|---|---|---|
| Game | Board | 组合 | 1 → 1 | 一局必有一堆牌；局结束重开时旧牌堆整个作废，生命周期完全被 Game 拥有 |
| Game | Tray | 组合 | 1 → 1 | 同上；槽位不能脱离对局存在 |
| Game | GameState | 组合 | 1 → 1 | 状态随对局生灭 |
| Game | Timer | 组合 | 1 → 1 | 计时器属于本次对局 |
| Game | UndoManager | 组合 | 1 → 1 | 撤销栈属于本次对局，重开即清空 |
| Game | PropManager | 组合 | 1 → 1 | 道具次数属于本次对局 |
| Board | Tile | **聚合** | 1 → 0..* | 关键差别：牌可以**离开**牌堆去槽位，牌的生命不随"离开牌堆"结束；故用聚合而非组合 |
| Tray | Tile | **聚合** | 1 → 0..7 | 牌同样可以离开槽位（被消除、被移出）；上限 7 来自 BR-02 |
| UndoManager | Command | 聚合 | 1 → 0..30 | 栈清空时命令被丢弃，但命令本身不依赖管理器存活；上限 30 来自 BR-06 |
| Command | Tile | 关联 | * → 1 | 命令必须记住"要撤销的是哪张牌" |
| Command | Tray | 关联 | * → 1 | 消除快照要记槽位中的位置，撤销时才能插回原序 |
| PropManager | Board | 关联 | 1 → 1 | 移出要问牌堆"最上层哪里有空位"，洗牌要改牌堆图标 |
| PropManager | Tray | 关联 | 1 → 1 | 移出要从槽位取牌 |
| PropManager | UndoManager | 关联 | 1 → 1 | 道具使用也要能撤销，故须入栈 |
| LevelGenerator | LevelConfig | 依赖 | 1 → 1 | 一次性读取参数，生成完即断开 |
| LevelGenerator | TileFactory | 依赖 | 1 → 1 | 造牌需要统一发号 |
| LevelGenerator | Board | 依赖 | 1 → 1 | 只负责"填"，不负责"持" |
| TileFactory | IconSet | 依赖 | 1 → 1 | 取图标定义 |
| LevelConfig | IconSet | 依赖 | 1 → 1 | 配置里只写"种类数 N"，具体是哪 N 种由图标库决定 |
| Repository | Board / Tray / Timer / PropManager / GameState | 依赖 | 1 → 1 | 只读取快照、只写回快照 |
| Renderer | Game | 单向依赖 | 1 → 1 | 把玩家意图转发给 Game |
| Renderer | Board / Tray / GameState | 单向依赖（只读） | 1 → 3 | 渲染需要读状态，但不回写 |
| Renderer | SoundPlayer / AnimationPlayer | 依赖 | 1 → 2 | 表现层的两个副作用执行者 |
| Game | Renderer | **无直接依赖** | — | 模型不依赖视图：Game 只发出"状态已变化"的通知，谁订阅谁负责刷新 |

> **表里最重要的一行是最后一行**。如果 Game 直接 `renderer.render()`，那么 §2 里所有"可测试性"的说法都会失效——模型测试就得先造一个 DOM。

### 3.2 重点：Tile 的坐标与层号属于谁？

这是本项目最值得辨析的一处设计分歧，因为它同时影响撤销、移出、存档三条路径。

**两种方案**

| 方案 | 内容 | 优点 | 致命问题 |
|---|---|---|---|
| A：Board 持有二维数组 | `board.grid[layer][cell] = tileId`，位置由数组下标表达，Tile 不记位置 | 覆盖判定天然是查表；不会出现"两份数据" | 牌离开牌堆（入槽）后，**它在数组中的位置信息随之丢失**；撤销要求"回到原层原格位"，此时只能靠命令额外记一份位置——等于位置仍然被复制到了命令里，只是绕了一圈 |
| B：位置属于 Tile 自身 | Tile 持 `layer / col / row`；Board 另维护**派生**的占用索引以加速查询 | 位置跟着牌走，撤销/移出/存档都只需读写牌本身 | 可能"双写不一致"：牌的坐标改了而索引没改 |

**选择：B，并加一条不变式来消灭 A 的唯一顾虑**

> **不变式 I-1（占用表一致性）**：∀ 牌 t，若 `t.state == board`，则 `occupied[t.layer][t.cell] === t`；反之若 `t.state != board`，则 `occupied` 中不含 t。
> **保证手段**：占用索引**只由 Board 的 add / remove 维护**，而这两者也是唯一允许修改 Tile 位置的地方——即"改位置"与"改索引"被强制绑在同一个入口里，外部无法只改其中一半。

**理由（三条，按重要性排序）**

1. **撤销的正确性**：BR-06 要求"牌回到原位"。位置若是 Board 的数组下标，撤销时必然要在命令里再存一份坐标，形成"同一事实的两份副本"，而恰好是命令里那份会随实现走样。
2. **移出道具的语义**：BR-07 要把牌放到"牌堆最上层空闲格位"。牌自身带坐标时，这一步就是"改三个数 + 让 Board 重建索引"，不需要在两套结构间搬移。
3. **存档的最小性**：BR-11 要求只存可重建的最小集合。Tile 自持位置时，存档就是"一串牌的状态"，恢复时逐张放回即可；若位置在数组里，存档必须同时存数组与牌表，且要保证二者版本一致。

**代价与对策**：代价是多了一份可派生的索引（空间 O(牌数)）。对策是把它当**缓存**看待——任何时刻都可以从全部 Tile 重建，因此它出错时可以被自检发现（在自检里遍历 Tile 比较索引）。

### 3.3 重点：Board 与 Tray 的分工

**分工表**

| 维度 | Board | Tray |
|---|---|---|
| 组织方式 | 无序（按层与格位建索引） | **有序**（顺序即语义，FR-12） |
| 核心问题 | 这张牌**能不能点**（覆盖） | 这些牌**是不是三个一样**（计数与配对） |
| 容量 | 无上限（随关卡） | 硬上限 7 |
| 判定产出 | 布尔（可点 / 不可点） | 结构事实（满 / 可消 / 溢出） |
| 终局角色 | 提供"是否已空"这一事实 | 提供"是否已满且不可消"这一事实 |
| 失败/胜利结论 | **都不下**——由 Game 下 | **都不下**——由 Game 下 |

**为什么不让 Tray 继承 Board**：二者唯一的相似点是"都能装牌"。但 Board 的核心行为（覆盖判定、层结构）对槽位毫无意义，槽位的核心行为（顺序、三消）对牌堆也毫无意义。继承会得到一个"槽位也支持分层"的荒谬模型，并在替换原则下立刻破产——槽位不是牌堆的一种。

**为什么不让 Board 同时管槽位**：那 Board 就会同时拥有"几何结构"与"配对语义"两个变化轴。后果是可预测的：撤销时要同时回滚"层结构"和"配对计数"，两者出错的表现不同（一个是牌悬空，一个是牌消失），排查难度翻倍。

**迁移规则（跨容器交接的唯一通道）**

> **规则 R-1**：一张牌在任一时刻只属于 Board 或 Tray 或已消除三者之一（`tile.state` 是唯一权威）。
> **规则 R-2**：牌在两个容器间迁移，必须由 Game 在同一段逻辑内完成"从 A 移除 + 加入 B"，禁止 Tray 自己去 Board 取牌。
> **规则 R-3**：迁移必须先**判定后执行**（先问 Board 能否点，再执行移除），保证不出现"移除了才发现点不动"的中间态。

> **R-2 的理由**：如果 Tray 能直接向 Board 要牌，那"点击入槽"这条流程就有两个发起者；而撤销需要知道"这一步是谁发起的、顺序如何"，双发起者会让命令的边界变得不可判定。

### 3.4 依赖方向与分层

```
       ┌──────────────────────────────────────────┐
       │  表现层  Renderer（+ SoundPlayer /        │
       │          AnimationPlayer）                │
       └───────────────┬──────────────────────────┘
                       │ 单向：转发意图 / 只读状态
       ┌───────────────▼──────────────────────────┐
       │  控制层  Game / GameState / UndoManager / │
       │          PropManager                     │
       └───────────────┬──────────────────────────┘
                       │ 单向：调用模型操作
       ┌───────────────▼──────────────────────────┐
       │  模型层  Board / Tray / Tile / IconSet /  │
       │          LevelConfig / LevelGenerator /   │
       │          TileFactory / Command            │
       └───────────────┬──────────────────────────┘
                       │ 单向：读取/写入快照
       ┌───────────────▼──────────────────────────┐
       │  数据层  Repository / Timer（服务）        │
       └──────────────────────────────────────────┘
```

**三条依赖纪律**

| 纪律 | 内容 | 违反后的症状 |
|---|---|---|
| D1 | 箭头只向下，不向上 | 模型里出现 `document` / `querySelector`，测试必须先开浏览器 |
| D2 | 模型层不知道控制层存在 | Board 里出现 `game.lose()`，槽位与流程双向依赖 |
| D3 | Command 只依赖模型层 | 命令里出现 `renderer.refresh()`，撤销变成"改数据 + 猜界面" |

## 4. 用例实现分析

用"玩家 → 控制器 → 对象"的协作序列还原三条最关键的流程。刻意保留**次序**细节，因为本项目最隐蔽的 bug 都在次序上（先消还是先判负、先扣次数还是先执行）。

### 4.1 用例一：点击一张牌并触发消除（UC-02 + UC-03）

| 步 | 参与者 | 动作 | 说明 |
|---|---|---|---|
| 1 | 玩家 | 在牌面上点击 | 只产生一个像素坐标 |
| 2 | Renderer | 把坐标映射为 `tileId`，转发 `Game.onTileClick(tileId)` | **视图只回答"点到了哪张"**，不回答"能不能点" |
| 3 | Game | 向 GameState 校验：当前是否 Playing、是否处于动画锁定中 | 动画锁定（FR-10）在此拦截连点 |
| 4 | Game | 向 Board 询问 `canPick(tile)` | 覆盖判定在 Board（BR-01） |
| 4a | Board | 返回 false → Game 通知视图播放"不可点"反馈 | 步数不变（AC-12） |
| 5 | Game | `Board.removeFromBoard(tile)` | Board 内同步维护占用索引（I-1） |
| 6 | Game | `Tray.append(tile)` | 追加到末尾（FR-12） |
| 7 | Game | `Tray.findTriple()` | 是否凑成三张 |
| 7a | Tray | 未凑成：返回空 | 继续步 10 |
| 8 | Tray | 凑成：取出那 3 张（含刚落下的这张），从槽位移除 | 顺序不重排（BR-03） |
| 9 | Game | 创建 `EnterTrayCommand`，记录：入槽的牌 + 原层原格位 + 被消的 3 张及槽位位置 | **关键**：消除快照必须进命令（见 §2.10） |
| 10 | Game | 步数 +1，`UndoManager.push(cmd)` | 步数只对成功入槽计数（FR-22） |
| 11 | Game | **先判胜**：Board 已空且 Tray 已空 → GameState = Won | 顺序见下方说明 |
| 12 | Game | **再判负**：Tray 已满且无可消 → GameState = Lost | AC-14 靠这个次序 |
| 13 | Game | 通知视图刷新 | Game 不直接调用 Renderer 的方法，只发通知 |
| 14 | Renderer | 重绘牌堆、槽位、HUD（剩余牌数、步数、计时） | 剩余牌数 = 牌堆 + 槽位（AC-34） |

**次序为什么必须是"先消 → 再判胜 → 再判负"**

- 若先判负：第 7 张牌恰好凑成三消时会误判为失败，直接违反 AC-14。
- 若先判负再判胜：局面清空时槽位必为空，不会误判；但若实现者先写判负，就会漏掉"最后一步同时满足清空"的情形。
- 结论：把"消除"作为入槽的**固有后置动作**，胜负判定放在消除之后，且胜优先于负。

**原子性要求**：步 5～10 必须构成一个整体——若中途异常（例如命令创建失败），不得留下"牌已离开牌堆但未入槽"的状态。实现上的对策是：先构造命令所需的数据（位置、图标、三张快照），再执行变更；任何一步失败就不开始执行。

### 4.2 用例二：撤销一步操作（UC-06）

| 步 | 参与者 | 动作 | 说明 |
|---|---|---|---|
| 1 | 玩家 | 点击撤销按钮 | — |
| 2 | Game | 校验：GameState 允许撤销（非终局）、非动画锁定 | BR-06 / BR-09 |
| 3 | Game | 校验：UndoManager 非空、PropManager 的撤销次数 > 0 | 两处都要查：栈空与次数耗尽的表现不同 |
| 4 | Game | `cmd = UndoManager.peek()` | 只看不弹 |
| 5 | Command | 依类型执行逆操作：<br>· EnterTrayCommand：把牌从槽位取出 → 放回 Board 的**原层原格位** → 若当时触发过消除，把那 3 张按原槽位位置插回<br>· RemoveCommand：从牌堆取下那 3 张 → 按原位置插回槽位<br>· ShuffleCommand：把牌的图标逐个还原为旧映射 | 逆操作的**粒度是一次操作**，不是一次点击 |
| 6 | Game | 若 `cmd` 是道具命令 → `PropManager.refund(道具类型)` | 归还被消耗的**道具次数**（BR-06） |
| 7 | Game | `UndoManager.pop()` | 弹出后该步不可再被撤销 |
| 8 | Game | 扣减撤销次数 | 撤销本身也是一种消耗 |
| 9 | Game | 刷新视图 | **步数不回退**（Q-05） |

**三个容易做错的点**

| 陷阱 | 后果 | 本设计的对策 |
|---|---|---|
| 撤销只把牌放回牌堆，忘了恢复被消除的三张 | 局面牌数变少，破坏 BR-04（3 的倍数），最终表现为"剩下的牌永远消不完" | 消除快照进命令（步 5） |
| 撤销归还了次数但没弹栈 | 可以无限撤销同一操作 | 先 peek 逆操作，再 pop（步 4 → 7） |
| 撤销后步数也减 1 | 与 Q-05 冲突，且"步数"在结算里要能反映真实操作量 | 步数只增不减（步 9） |

**为什么用命令而不是"每步存全量快照"**：全量快照最省事，但 144 张牌 × 30 步 = 4320 条记录的复制开销，且无法回答"这一步消耗了哪种道具"（要逐字段 diff）。命令模式把"逆操作"与"归还什么"一起编码，代价是每个新操作都要新写一个命令类——但这个项目的操作种类是封闭的（入槽 / 移出 / 洗牌），代价可控。

### 4.3 用例三：洗牌后重排（UC-08）

| 步 | 参与者 | 动作 | 说明 |
|---|---|---|---|
| 1 | 玩家 | 点击洗牌按钮 | — |
| 2 | Game | 校验 GameState 与道具可用性 | 终局禁用（BR-09） |
| 3 | PropManager | 校验洗牌次数 > 0；不足则触发"已用完"提示 | FR-20 |
| 4 | PropManager | 扣减洗牌次数 | **先扣后做**：避免执行成功但次数没扣 |
| 5 | Board | `collectIcons()`：收集全部未消除牌的图标（只收牌堆里的，槽位中的不参与） | 关键边界：洗牌**不动槽位**，否则会凭空造出三消 |
| 6 | Game | 打乱这串图标 | 打乱算法在 Game/工具，不放在 Board（Board 不关心随机性） |
| 7 | Board | `applyIcons(shuffled)`：按**确定的遍历顺序**回填，位置、层号、占用索引一律不变 | BR-08：只换图标，不改结构 |
| 8 | Game | 创建 `ShuffleCommand`，保存"牌 → 旧图标"映射 | 撤销靠它 |
| 9 | Board | 自检 BR-04（每种图标仍为 3 的倍数） | 图标总数没变，理论上必过；但自检是廉价的保险 |
| 10 | Game | 通知视图刷新（图标变化、次数变化） | 牌的位置不动，动画只需换图标 |

**为什么洗牌只收"牌堆里的图标"**：若把槽位里的牌也纳入重排，会出现"槽位里本来有两张同图标，洗牌后变成三张"——凭空消除，直接破坏 BR-04 与公平性。反过来，如果只重排牌堆，槽位中的两张同图标牌仍在那里，玩家仍可去找第三张，语义自洽。

**这里藏着一个需求级冲突**（→ 遗留问题 P-02）：BR-08 要求"不改变结构"，BR-12 要求"保证可解"。但**可解性依赖图标分布**——只重排图标完全可能把局面变成死局（例如把某三张同图标全压在最深层、而它们上方恰好需要那三张才能开）。洗牌本意是"救急"，却可能让局面更糟。这不是实现 bug，是两个需求条款的张力，必须在设计阶段给出明确对策（例如洗牌后跑一次轻量可解性检查并重试，或把 BR-08 的承诺放宽）。

## 5. 覆盖判定算法分析

### 5.1 问题定义

给定牌堆状态（哪些牌还在、各自在哪层哪格），判定"玩家点到的这张牌现在能不能被拿走"。要求：不依赖界面、可单独验证、结果与视觉一致。

### 5.2 思路一：按渲染几何相交

**做法**：每张牌在屏幕上有真实矩形（位置由渲染算出、含抖动偏移）；一张牌可点 ⇔ 不存在"未消除、层号更高、矩形与其**有面积重叠**"的牌。

| 项 | 评价 |
|---|---|
| 优点 | 与玩家所见**严格一致**；不需要额外维护层级结构；实现直接（读 DOM 的 offsetLeft/offsetTop 即可） |
| 缺点 | ① 判定依赖渲染结果，窗口缩放、DPI 变化、CSS 改动都会改变判定，同一份逻辑在 1920 与 1366 下结论可能不同；② 抖动（FR-06）一旦调大，会出现"看着没压住却点不动"；③ 测试必须在浏览器里构造像素坐标，无法写成纯函数单测（违反 NFR-08）；④ 每次判定要遍历全部高层牌并算矩形相交，144 张牌时是 O(n) 且含浮点 |
| 适用 | 快速原型；或作为**生成期的体检工具**（生成后抽样比对"几何判定"与"模型判定"是否一致，用于发现配置错误） |

### 5.3 思路二：按层号 + 整数格位

**做法**：把"位置"表达为**模型内的整数坐标**，与像素完全无关。

- 每张牌有 `layer`（层号）与 `cell`（该层内的整数格位）。
- 层与层之间有固定的**半格错位**（这是"叠"的视觉来源）。把坐标统一放大 2 倍（以半格为单位），则错位量变成整数，所有牌的覆盖范围都是整数矩形。
- 预先为每层建立**占用索引**：`occupied[layer][cell] → 牌`。
- 一张牌占用的"向上投影格位集合"由错位规则**推导**得出：半格错位下，一张牌最多覆盖其上方一层中的 4 个格位（左上 / 右上 / 左下 / 右下）；错位为 0 时只覆盖 1 个。
- 抖动（FR-06）**不进这套坐标**，只影响渲染偏移；并由"抖动幅度 ≤ 牌宽/6"这一约束保证视觉上不会误导玩家（FR-06 已写死）。

**判定过程（语言无关，仅描述步骤）**

```
canPick(t):
  ① 若 t 不属于牌堆（已在槽位或已消除）→ 返回 false
  ② 对每一层 k，从 t.layer+1 到最高层：
       ③ 取 t 在 k 层上的投影格位集合 P（由错位规则派生，元素数 ≤ 4）
       ④ 对 P 中每个格位 c：
            ⑤ 若 occupied[k][c] 存在且该牌仍在牌堆 → 返回 false
  ⑥ 返回 true
```

| 项 | 评价 |
|---|---|
| 优点 | ① **纯整数、纯函数**：不碰 DOM，可在控制台直接调用验证（NFR-08、AC-04 的同类做法）；② 与窗口尺寸、DPI、抖动完全解耦（BR-01 的字面要求）；③ 复杂度是"层数 × 每层最多 4 格"≈ 常数（挑战关 8 层 × 4 = 32 次查表），与总牌数无关；④ 判定与渲染的一致性由"错位规则只有一处定义"保证——层间错位量同时驱动渲染坐标与投影格位 |
| 缺点 | ① 需要维护占用索引，多一份可能不一致的数据（用不变式 I-1 约束）；② 错位规则若与 CSS 里的偏移量各写一份，会漂移（对策：偏移量只在一处定义，渲染与投影都从它派生）；③ 无法表达"非整数错位"的特殊布局（本项目不需要） |
| 适用 | 本项目：判定是业务规则（BR-01 明确要求与渲染无关），必须走这条路 |

### 5.4 比较与取舍

| 对比项 | 思路一 几何相交 | 思路二 层号 + 整数格位 |
|---|---|---|
| 判定依据 | 渲染结果（像素） | 模型状态（整数） |
| 与窗口/DPI/抖动的关系 | 受影响 | 完全无关 |
| 能否纯函数单测 | 不能（需 DOM） | 能 |
| 单次复杂度 | O(高层牌数)，含浮点 | O(层数 × 4)，纯整数 |
| 视觉一致性 | 天然一致 | 需保证"错位规则单一来源" |
| 维护成本 | 低（不用索引） | 中（需索引 + 不变式） |
| 出错时的表现 | 偶发、随窗口变化、难以复现 | 结构性、可被自检发现 |

**选择：思路二。** 三条理由按权重排序：

1. **BR-01 已经把答案写死了**——"判定只读模型（层号 + 整数格位），与渲染坐标、抖动、窗口缩放无关"。选思路一等于违反已冻结的需求。
2. **可测试性优先于实现便利**：思路二允许把"覆盖判定"作为纯函数在控制台穷举验证（例如构造 3 层小牌堆，逐张断言），这是 AC-06/AC-07 能稳定复现的前提。
3. **视觉一致性可以用工程手段保证**：把"层间错位量"定义成唯一常量，渲染与投影格位都从它派生，一致性就从"靠人工对齐"变成"靠单一来源"。

**思路一不丢弃**：它降级为**生成期体检工具**——生成完一关后，随机抽若干牌，用真实渲染矩形算一次相交，与模型判定比对；不一致说明错位规则或抖动幅度有问题。这样两种思路各得其所：一个守运行时正确性，一个守视觉一致性。

## 6. 状态与不变式

### 6.1 GameState 状态与迁移

| 当前状态 | 允许的操作 | 可迁移到 | 触发条件 |
|---|---|---|---|
| Idle（选关界面） | 选关 | Ready | 玩家选定关卡且生成成功 |
| Ready（已生成，未落子） | 开始 | Playing | 首帧渲染完成或玩家首次点击 |
| Playing | 点击、道具、撤销、暂停、重开 | Playing / Paused / Won / Lost | 见右 |
| Paused | 继续、重开 | Playing / Ready | 玩家继续或重开 |
| Won | 重开、返回选关 | Ready / Idle | — |
| Lost | 重开、返回选关 | Ready / Idle | — |

**禁止的迁移（必须在实现中拦截）**

| 非法迁移 | 为什么必须拦 |
|---|---|
| Won / Lost → Playing | 终局锁定（BR-09）；否则玩家能靠"再点一下"复活 |
| Paused → Won / Lost | 暂停时不该有任何判定发生（BR-10 的延伸） |
| Playing → Ready（不经重开） | 会绕过道具次数重置（BR-13） |

### 6.2 不变式清单

这些不变式在系统设计阶段会变成自检函数，在此先定义清楚"什么必须永远为真"。

| 编号 | 不变式 | 关联需求 | 违反后的可观察症状 |
|---|---|---|---|
| I-1 | 占用索引与 Tile 的 state/position 一致 | BR-01 | 牌看着能点却点不动，或已消除的牌仍"压"着别人 |
| I-2 | 每张牌恰好属于 board / tray / cleared 之一 | R-1 | 牌"消失"或"重复出现" |
| I-3 | 每种图标的牌数 % 3 == 0（含槽位中未消除的牌） | BR-04 | 最后剩 1～2 张永远消不掉，无法通关 |
| I-4 | 槽位长度 ≤ 7 | BR-02 | 槽位溢出仍可继续，失败判定失效 |
| I-5 | 撤销栈长度 ≤ 30，且只含已成功执行的操作 | BR-06 | 撤销出"幽灵操作"，局面与操作历史不符 |
| I-6 | 暂停期间累计毫秒不变 | BR-10 | 暂停后时间仍在走 |

### 6.3 生命周期：一局游戏的对象生灭

| 阶段 | 新生 | 死亡 | 说明 |
|---|---|---|---|
| 进入关卡 | Game、Board、Tray、Timer、UndoManager、PropManager、GameState | 上一局的同名对象 | 组合关系的直接体现：一局一套 |
| 开局 | Tile（由生成器批量创建）、Command（每次操作一条，随撤销弹出而减少） | — | 牌是一次性对象，消除后不回收复用 |
| 重开 | 重新创建整套对局对象 | 旧牌堆与旧撤销栈整体废弃 | 不做"就地重置"：重置逻辑容易漏字段（例如忘了清消除快照） |
| 返回选关 | — | Game 及其组合对象 | 存档保留，故下次进入可恢复 |

> **后续状态（2026-10-31 补记）**：P-01～P-06 已在 `docs/04-系统设计.md` §10.1 全部给出结论（P-01 步数归 Game；P-02 洗牌改为按 group 整组置换；P-03 结算文案改为"步数（入槽次数）"；P-04 引入溢出层；P-05 补音效触发表；P-06 求解器离线交付）。本表保留问题原貌，结论不在此处修改。

| P-06 | 可解性验证物（求解器）是否随代码交付 | AC-33 需要求解器验证，但它是测试工件 | 若放进产品代码，会污染分层；若不交付，AC-33 无法复现 | 设计阶段定为独立目录（如 `tools/`）的离线脚本，不进运行时，报告里说明其用途 |

| D-04 | 胜负判定放在哪 | ①Tray 自己判 ②Game 据 Tray 报的事实判 | ①会让模型层反向依赖控制层（Tray 要知道"输了"这个游戏语义），撤销时无法界定终局归属 | Tray、Game、GameState |
| D-05 | Board 与 Tray 的关系 | ①Slot 继承 Board ②各自独立、由 Game 交接 | 二者仅有"能装牌"这一相似点，继承会让"槽位支持分层"这种荒谬结构成立，违背替换原则 | Board、Tray、Game |
| D-06 | 模型与视图的依赖方向 | ①Game 直接调 Renderer ②Game 只发通知 | ①使模型测试必须依赖 DOM，直接摧毁 NFR-08；②让"换渲染方式"只改一个类 | Game、Renderer、NFR-06 |
| D-07 | 可解性如何保证 | ①随机铺牌后求解验证，失败重试 ②按可解序列反向铺牌 | ①在高难度关卡上重试次数不可控（可能长时间生成失败）；②一次成功、可证明，且能支撑 AC-33 | LevelGenerator、AC-33 |
| D-08 | 游戏状态的表达 | ①多个布尔标志 ②单一状态 + 迁移表 | 布尔组合会产生 8 种状态中的 5 种非法态；单一状态可把非法态消灭在类型层面 | GameState、Game、Renderer |
| D-09 | 道具效果的归属 | ①PropManager 自己实现三种效果 ②只做次数与准入，效果委托 Board/Tray | ①会让一个类同时依赖"布局算法"与"洗牌算法"，成为最难改的地方；②效果留在拥有数据的对象上 | PropManager、Board、Tray |
| D-10 | 存档的职责边界 | ①Repository 直接 new 出对象 ②只搬纯数据，类自己恢复 | ①版本升级时 Repository 成为唯一爆炸点，且它要知道所有构造细节；②符合 NFR-06 分层 | Repository、Tile、Board、Tray |
| D-11 | 洗牌是否重排槽位中的牌 | ①牌堆 + 槽位一起重排 ②只重排牌堆 | ①会凭空造出三消（槽位两张同图标 + 洗牌凑成第三张），破坏 BR-04 与公平性 | Board、Tray、PropManager、BR-05 |
